# Columbus: technical reference

How Columbus works in detail: what it enforces and how, every tool family, connected servers, confinement, the app, connections, building, tests and limits. For what Columbus is and a tour of the app, see the [README](../README.md).

Columbus makes a GIS analyst, paired with whatever AI their organization already licenses, faster and more trustworthy at real work on real data. This repository holds the core of it: **`columbus-mcp`, a governed GIS MCP host** that any MCP agent (Copilot, Claude, Codex, Gemini CLI, Cursor) can use. It runs its own GIS engines and connects to other MCP servers (Drive, notes, vendor APIs), and every capability, native or connected, passes the same permissions, approvals, data-flow rules, audit and provenance, enforced in its own code.

> **Status: test releases; this describes 0.14.0.** The governance core, read-only and read-write connections (PostGIS, Oracle, SQL Server, GeoPackage, SQLite, raster folders), read-only shapefiles, file geodatabases, folders of files (CSV, Excel, GeoJSON, GeoParquet, KML, FlatGeobuf) and ArcGIS Online/Portal services, geoprocessing with checks, file geodatabase and GeoTIFF exports, Python environments, connected MCP servers, personal tools, workflows, web map layers, map snapshots and the desktop app work end to end. Trusted Python environments and arcpy are **experimental** (D-13) until checked on a real ArcGIS Pro machine ([manual checks](manual-checks.md), H-2). What 0.14.0 does not do is under [Not in this release](#not-in-this-release).

## Principles in code

- **Rules live in the server, not the prompt.** The agent can ask for anything; the server decides. It has no tool that reads or changes policy or connections.
- **Read-only by default.** Edits stay off until organization policy turns them on; until then every connection is read-only whatever it says.
- **Access is an intersection.** Organization policy ∩ connection ∩ data group ∩ project. Each layer can only narrow the one above (the organization alone may raise row and time limits, within a ceiling in code).
- **Show your work.** Every result carries `result`, `checks` and `provenance`; every call writes one line to a hash-chained audit log, including refusals.

## Policy keys added in 0.15 (F-15)

From `docs/build-brief-3.md`. All optional; a switch that is absent is off.

| Key | Default | What it does |
| --- | --- | --- |
| `scripts.approval` | `each` | When a script that runs in the sandbox with no network (confinement level A: the engine's Python, or a governed level-A environment) asks the person first: `each` run, once per `session` for the same code, or `none` (it runs at once; the sandbox is the boundary). Absent, it is `session` when `scripts.session_approval` is `true`, else `each`; stated, it wins over the older key. A level B run and a trusted run ask every time, whatever it says ([The boundary](#the-boundary-d-16)) |
| `allow_toolboxes` | `false` | [Toolboxes](#toolboxes) (programs that describe their own tools) may be installed and used |
| `toolboxes.catalogue` | `true` | Columbus's built-in catalogue may download a toolbox the person chooses to install; `false`, toolboxes are added only from files already on the computer |
| `allow_project_files` | `false` | The assistant may list, read and write text files in its project's own folder, and run scripts kept there |
| `allow_sync` | `false` | A project's files may sync with a Git server, on the person's click |
| `sync.hosts` | `[]` | Git servers a project may sync with, by host name; empty means any server the person connects |

Unknown keys inside `scripts`, `toolboxes` and `sync` are refused, and so is a value of `scripts.approval` other than the three (the message names `scripts.approval` and the three values). `scripts.approval` and `allow_project_files` are in force from this build on ([Project files](#project-files)). `whoami` reports all six under `policy`: `script_approval` (`each`, `session` or `none`) with `script_approval_means` (a sentence for the assistant), `toolboxes_allowed`, `toolbox_catalogue`, `project_files_allowed`, `sync_allowed` and `sync_hosts`; the app's Settings read (`settings_state`) carries `script_approval`, `work_mode` (`free`, `ask` or `off`), `allow_toolboxes`, `allow_project_files`, `allow_sync` and `environments_allow`, and Settings › Organization rules says each in plain words.

**Work freely on copies.** The app offers one choice, in the first-run setup, at the top of Settings and in Settings › Organization rules: **Work freely on copies** (recommended) or **Ask me before each script**. Choosing the first writes seven settings to the policy file after one confirmation at the keyboard (Touch ID, the account password or Windows Hello, as for every switch): `allow_scripts: true`, `scripts.approval: none`, `environments.allow: true`, `allow_personal_tools: true`, `allow_toolboxes: true`, `allow_project_files: true` and `allow_sync: true`. Choosing the second sets `scripts.approval: each` and changes nothing else: the other six stay as they are, and each has its own switch. The cards show the mode in force: on while `allow_scripts` is on and `scripts.approval` is `none`. Where the policy file is not the person's to change (this account cannot write it), the cards are shown, not offered, with "This is set by your organization"; where there is no policy file, Columbus's strict defaults apply and the cards say to create one first, as the switches do. The app changes only those lines: top-level switches as before, and the two grouped settings whether their group is written on one line (`scripts: { session_approval: true }` becomes `scripts: { session_approval: true, approval: none }`), as an indented block (the line is changed in place, or added as the block's first line at its own indent), or not at all (a block is added at the end); comments are kept. Before anything is saved, the old and the new text are read as YAML and must differ in exactly those settings; a layout the app cannot change safely is refused with the lines to write by hand, and a file the server would not load is put back.

**How `sql_select` is checked.** The SQL must parse, in the connection's dialect (Oracle, PostgreSQL, SQL Server, SQLite, DuckDB; shapefiles and file geodatabases use SQLite's, and run in GDAL's SQLite dialect over their layers), as exactly one `SELECT`. Every table, including those in subqueries, must be on the connection's allow list and off its deny list; quoting does not get around this. System catalogs (`pg_catalog`, `information_schema`, `sys`, Oracle's `DBA_`/`ALL_`/`V$` views, `sqlite_master`) are refused even under an allow-everything pattern. `WITH`, `SELECT INTO`, `FOR UPDATE` and table functions are refused. Only ordinary scalar, aggregate and window functions and the database's own spatial functions may be called (an allow list; on PostgreSQL a spatial function counts only when the PostGIS extension installed it, whatever its name; on Oracle only Oracle's built-ins, never a name Oracle lacks (which would resolve to whatever function or synonym someone created), and Oracle Spatial's `SDO_RELATE`, `SDO_FILTER`, `SDO_WITHIN_DISTANCE`, `SDO_GEOM.*` and a few `SDO_UTIL` conversions, always rewritten to be called in `MDSYS`; on SQL Server only unqualified built-ins, so geometry methods such as `geom.STIntersects(...)` and `geometry::Point(...)` are refused, because the parser cannot tell `col.Method()` from `schema.function()`; GeoPackage and SQLite files are opened without spatial functions; there, and for SQL Server geometry, spatial questions go to `query_features` and `vector_op`). `TABLESAMPLE` is refused rather than silently dropped. Custom operators and casts to types the database defined are refused: functions that run SQL given to them as text (`query_to_xml`, `ts_stat`), read a table by name (`table_to_xml`, `ST_EstimatedExtent`), or reach files, the network or server internals would read outside every check, and the database's own functions can do anything. The server then rewrites every table reference into a filtered derived table, so the connection's row filter and data-group filters always apply, and adds a row limit with one sentinel row so truncation is detected and reported rather than returned as a complete result. The worker opens the source read-only as well: SQLite files in read-only mode, PostgreSQL sessions with `default_transaction_read_only` and a statement timeout, so even a `SELECT` that calls a writing function is stopped by the database. Oracle sessions are set read-only (`READ_ONLY` on 23ai and later), cannot commit from PL/SQL (`DISABLE COMMIT IN PROCEDURE`, which also stops an autonomous transaction in a function a query calls) and run `SET TRANSACTION READ ONLY` with a call timeout. SQL Server has no read-only session: each query runs with `ApplicationIntent=ReadOnly` and a query timeout inside a transaction that is always rolled back, so a read-only login is the real guarantee there. Anything that does not parse is refused, never passed through, and the SQL that runs must read back, parsed and written out again, as exactly itself (the parser drops the quotes of a type modifier and does not escape `]` in a `[name]`, which could otherwise turn a value into SQL no check saw).

**GIS tools.** `query_features` builds its SQL from named fields (checked against the dataset, hidden fields refused) and a `where` clause that may use only comparisons, AND/OR/NOT, IN, LIKE, BETWEEN, IS NULL and simple functions, then runs it through the same checks as `sql_select`. Every result is a layer in the session workspace (GeoPackage, or CSV without geometry), passed to the next tool as a `ws://` handle, labelled with where its data came from, and recorded with a provenance file. `vector_op` reads a dataset input through the same permissions and refuses one cut off at the read limit, because processing part of a dataset gives wrong answers silently; a layer that was cut off when it was made carries an `input.truncated` warning into everything built from it. The GIS tools open only layers Columbus's own engine, an approved engine plugin or an approved script wrote, and check each one by its content, never its name: a file saved from a connected server's result is refused, and GDAL formats that can point at other files or URLs (VRT and the like) are switched off in the engine. Every result carries checks (design section 4), for example:

**M and Z values (REQ-24).** Measures (M) and elevations (Z) are kept end to end. `query_features` and `sample_rows` read them from every engine: PostGIS's EWKB as it is; Oracle's `SDO_GEOMETRY` as the database's WKB, except LRS geometries (an L digit in SDO_GTYPE, such as 3302, 3306 or 4402), which the engine builds itself from `SDO_GTYPE`, `SDO_ELEM_INFO` and `SDO_ORDINATES` with the measure as M (and Z beside it for 44xx), because `SDO_UTIL.TO_WKBGEOMETRY` writes them as 2D; measured points, multipoints, lines and multilines of straight segments are read, and an LRS geometry with arcs, compound or polygon elements is refused with a plain error naming the column rather than read with wrong coordinates; SQL Server through `AsBinaryZM()` (not `STAsBinary()`, which drops both); GeoPackage, SQLite, shapefiles, file geodatabases and `files` datasets (whose cache GeoPackage keeps them) as stored. Results are written, in memory or streamed, as ISO WKB with the GeoPackage's `z`/`m` flags set, and every workspace layer with M is read back with its M (through Arrow; the check of the GeoPackage's `m` flag opens it with a SQLite URI that handles Windows drive, UNC and `\\?\` paths, and a layer whose flag cannot be read is read through Arrow too), so `vector_op` `reproject` (x, y and z transformed, M copied), `clip`, `join`, `spatial_join`, `dissolve`, `intersect` and `make_valid` keep them, as do exports to `gpkg`, `gdb`, `shp` and `fgb` (written as ISO WKB with a measured geometry type; GeoJSON has no M and drops it) and CSV's `wkt` (`LINESTRING M (...)`). Operations that build new vertices (`buffer`, `simplify`) drop M and say so with `geometry.m_dropped` (info). Engine plugin extracts hand over the geometry as read; the Python SDK's `Geometry` has `has_z`, `has_m`, `vertices` (each vertex with its Z and M) and `measures()`. A personal tool gets the layer file with its M; it reads them with `gpd.read_file(..., engine="pyogrio", use_arrow=True)` (pyogrio's plain read drops M). The map and companion window draw in 2D: their GeoJSON leaves Z and M out, and nothing fails on them. The engine needs shapely 2.1 or later.

**`vector_op` `filter` (AF-21, REQ-29, F-12).** `{op: filter, inputs: {layer: <handle or dataset>}, params: {where}}` keeps the rows a where clause selects, as a new layer (the input is unchanged; provenance records the where). The where goes through `query_features`' parser and subset (comparisons, AND/OR/NOT, IN, LIKE, BETWEEN, IS NULL, simple functions; no subqueries), is re-rendered in SQLite's dialect, and is refused before anything is read if it names a field the policy's `hide_fields` hides; `filter` takes no other params. The engine runs it against the layer's attributes in a private in-memory SQLite table (dates as ISO text), so a field the layer lacks is refused plainly; geometries are untouched (M and Z kept). Checks: `filter.rows` (info, kept of total) and `filter.empty` (warn). No approval: nothing leaves the workspace; the result carries its input's labels.

| Check | Catches |
| --- | --- |
| `crs.measure` | Buffering or simplifying in degrees; refused, with the projected CRS to use for the data's area |
| `crs.area_of_use` | Coordinates outside the CRS's area, including swapped X/Y and feet read as degrees |
| `crs.present` | No CRS: a fail for workspace layers and most sources; a warning on a `files` dataset and its `query_features` result (the connection's `crs` can supply one); info on a CSV or sheet without geometry |
| `file.encoding`, `csv.headers`, `xlsx.formulas`, `xlsx.errors` | A `files` CSV that isn't UTF-8 (read as Windows-1252; warning, naming the encoding), renamed blank or repeated headers (info), formulas with no saved value and Excel error cells (warnings) |
| `crs.agreement` | Inputs in different CRSs (aligned to the first, and said so) |
| `join.unmatched`, `join.many_to_many`, `join.key_types` | Keys that do not match (with the padding or spacing-and-case fix when that is why: join again with `key_as_text`, `pad`, `trim`, `ignore_case`), a number key joined to a text key, and joins that multiply rows |
| `filter.zero_rows`, `filter.all_rows` | A filter that keeps nothing, or everything |
| `geometry.valid`, `geometry.empty`, `geometry.duplicates`, `geometry.mixed_types` | Bad or surprising geometry |
| `geometry.m_dropped` | An operation that builds new vertices (`buffer`, `simplify`, or any whose output lost the input's M) dropped the input's M (measure) values (info) |
| `query.read_limit`, `input.truncated` | A result cut off at the limit, and anything built from one |
| `raster.nodata`, `crs.geographic` | A raster with no nodata value (fill values read as data), or in degrees (terrain needs a projected CRS) |
| `raster.resampling` | An integer raster (classes, codes) resampled with bilinear, cubic or average |
| `zonal.outside`, `zonal.no_pixels`, `zonal.cell_size` | Zones off the raster, zones with no valid cell, and cells too large for the zones (median under 10 cells) |
| `export.needs_pro_3_2` | A `gdb` export kept whole numbers beyond the 32-bit range exact as 64-bit integers (info): ArcGIS Pro 3.2 or later is needed to open it |
| `output.too_large` | A raster output over 400 million pixels, or the read limit x 1,000 if smaller; refused, with the fix to clip first |

Severities are `info`, `warn` and `fail`. A `fail` means the result should not be used as it is.

**Rasters.** A `rasters` connection is a folder of GeoTIFFs; a dataset is a file's path in it with forward slashes (`dem/travis_1m.tif`), under the connection's allow and deny lists. The gateway refuses names with `..`, an absolute path, `\` or `:`, resolves the name inside the folder after following every link and requires the result to be the very file the name spells (so a symlink or junction cannot lead out of the folder, or to a file the lists do not name), and checks its first bytes are TIFF's: GDAL picks a driver from a file's content, so a ".tif" holding VRT XML could otherwise read any file. The worker checks the bytes again, opens it with the GTiff driver only, never with open options or `/vsi` paths, and keeps VRT switched off. `raster_op` takes those files (`"dem:dem/travis_1m.tif"`) or the handles of earlier raster results, and layers (masks, zones) as `vector_op` does. `reproject` needs an explicit `resampling`; `slope`, `aspect` and `hillshade` need the elevations' `z_unit` (the z-factor comes from the CRS's horizontal units) and are refused in degrees or Web Mercator; `zonal_stats` writes the zones with their statistics as a layer. Outputs are Cloud-Optimized GeoTIFFs (DEFLATE) in `results/`, labelled with the connections they came from and checked for CRS and nodata. The size limit is 400 million pixels per output (and per read for `zonal_stats`), or the read limit (`limits.rows`, the tighter of the organization's and each raster connection's) times 1,000 if that is smaller. `export_output` exports a raster result as `tif` (below).

**Exports.** `export_output` writes only to the folders the organization lists in policy (`exports: [{id, path, granted}]`), under a plain file name. Before writing it runs the layer's checks, the delivery spec's (`delivery: <context pack entry>`: CRS, field renames, formats, required metadata) and looks back through every step the layer was built from: a `fail` anywhere, or a layer cut off at a row limit, blocks the export unless the person approves an override. A folder marked `granted` needs no approval otherwise; any other folder, replacing a file, or a flow rule (`to: [folder:<id>]`) asks the person. The approval is bound to the request and the exact source content. Files are created new, never written through an existing link, and `<name>.prov.json` beside them records the sources, steps, checks, metadata and approval. **Formats:** `gpkg` (the default), `gdb`, `geojson`, `fgb`, `shp` and `csv` for layers, `tif` for raster results (a delivery spec may also say `GeoPackage`, `FlatGeobuf`, `Shapefile`, `File Geodatabase`, `FileGDB`, `FGDB`, `GeoTIFF`, `TIFF` or `COG`). *`gdb` (R-8)* writes a new `<name>.gdb` with one feature class named `<name>`, through GDAL's OpenFileGDB driver; the name must then be a feature class name (a letter, then letters, digits and `_`), field names over 64 characters are refused with their list, and names the format does not allow are changed by it and listed (`export.field_names`, warn). Whole-number fields whose values all fit in 32 bits are written as 32-bit integers, readable by every ArcGIS; if any value is beyond that range, the layer is written with `TARGET_ARCGIS_VERSION=ARCGIS_PRO_3_2_OR_LATER` so 64-bit values stay exact, and an `export.needs_pro_3_2` info check names the fields (ArcGIS Pro 3.2 or later opens it). An existing `<name>.gdb` (any case) is never replaced or changed: any export of that name, in any format, with `overwrite` or approval, is refused (choose another name); other files of the same name follow the usual overwrite rule. *`tif` (R-9)* is for raster results only: the workspace's Cloud-Optimized GeoTIFF is copied byte for byte (one that is not a COG is rewritten as one, `export.cog`), keeping its CRS and nodata. A delivery spec's CRS must already match: rasters are never reprojected on export, and a different one fails with "reproject first (raster_op reproject)". A vector layer as `tif`, or a raster in any other format, is refused.

**Scripts.** `run_python` is off unless organization policy sets `allow_scripts: true`. The script runs only confined at level A through `columbus-confine` (AppContainer and a job object on Windows; the system sandbox on macOS; Landlock and seccomp on Linux): its own run folder under `runs/` is the only folder it can write, the Python installation the only other one it can read, it has no network, and its memory (`plugins.memory_mb`) and processes are capped. If the machine cannot confine it, it does not run, whatever `servers.allow_unconfined_local` or `scripts.approval` says (with no launcher: "…Columbus never runs a script unconfined"; with a launcher that cannot set the sandbox up: "the script could not be started confined, so it did not run"). That sandbox is the boundary ([below](#the-boundary-d-16)); whether the person is also asked first is the policy's `scripts.approval` (F-15). With `each`, the default, every run needs the person's approval: the card (in the client's own prompt or on the approvals page) shows the full code, the inputs and the data labels in play, and the approval is bound to the code's SHA-256, each input's content hash and the time limit. With `session` the card also offers the session approval (below). With `none` a run starts at once, without a card: its audit lines (`running`, then `allowed` or `error`) and its provenance step carry `scripts.approval: none` as the approval, so the log says which rule let it run. A run that leaves the sandbox asks every time under every value: a governed environment at level B (network) and a trusted environment; a workflow run never runs a script. `whoami` (`policy.script_approval`), `search_tools` (`approval` is `yes`, or `if_outside_sandbox` under `none`) and `describe_tool` ("In force now: …") tell the assistant which rule is in force. Its environment is cleared (no secrets, no `COLUMBUS_*` settings, PROJ and GDAL network and VRT drivers off). Inputs are workspace files a Columbus tool recorded in this session (never a connected server's), copied into `in/` with their content checked against what was recorded. The time limit (default 120 s, at most `limits.seconds`) ends the script and everything it started. Every plain file it leaves directly in `out/` is copied, without following links, to a new file in `results/` and recorded with the hash of the bytes copied; links, folders and oversized files are skipped and reported (`script.output_skipped`). Outputs carry the inputs' and the session's data labels, the inputs' fails and truncation, and the run's own fails (`script.exit_code`, `script.timeout`), so a failed run blocks export. GeoPackage and CSV outputs are checked as layers. stdout and stderr come back, 64 KB each. Provenance records the code, the inputs and their hashes, the exit code, the approval and the outputs. The engine's Python has geopandas, shapely, pyproj, rasterio and pandas; ArcPy is not available there. With `environment`, the script runs in a registered environment instead, under the same rules (below), except that a trusted environment (experimental, where policy allows it) runs unconfined, as the person.

### The boundary (D-16)

Columbus keeps one boundary in place of asking about each script. It is always true, and no setting loosens it:

- **B1. Connections stay with Columbus.** Passwords are in the operating system's credential store. The assistant, its scripts and its tools never get a password, a connection file, the credential store, or a way to open a network connection.
- **B2. Reading goes through Columbus**, under each source's rules (read-only or read-write, which rows and fields, limits). What is read lands as a copy in the chat's workspace.
- **B3. Inside the workspace the assistant works freely.** Where the policy says `scripts.approval: none`, scripts in the engine's Python or a governed level-A environment run without asking, in the sandbox: no network; they read the copies they are given and the Python installation; they write only their own run folder. A script can spoil a copy, never a source.
- **B4. Columbus asks only when something would cross the boundary:** a copy leaving the workspace (an export to a folder that isn't granted, a download from a host not on the list); a change to a real source (edits, each change set); code that wants the network or must run outside the sandbox (a level B environment, a trusted environment, arcpy); something new being installed (a personal tool and its test run, a workflow, a connected server, an environment).
- **B5. An organization can keep it stricter** in its policy file: `scripts.approval: each` (the default) or `session`, `allow_scripts: false`, and each of the other switches.

The code's defaults do not change: everything is off until the policy says so, and `scripts.approval` is `each` unless stated. The app's **Work freely on copies** writes the open settings after the person confirms at the keyboard ([above](#policy-keys-added-in-015-f-15)).

**The proof.** [`tests/boundary.rs`](../crates/gateway/tests/boundary.rs) runs a real script through `run_python` at level A under `scripts.approval: none`, in CI on Linux (where it fails, rather than skips, if the sandbox cannot be set up) and on macOS and Windows wherever the runner can set the sandbox up. The script, and a program it starts, try to list and read the connections folder, read the policy file, list the audit log, list and read another running session's workspace and this session's own results, list the person's real home folder and read and write a file there, read the gateway's environment and command line (Linux), connect to a port this computer listens on and to a public address, send UDP, look a host name up (asserted on Linux), write or delete outside the run folder (the workspace, `results/`, the other session, the connections folder, the policy file), and change the permissions and times of the policy file, a connection file and the other session's result. Every attempt must fail (on Linux a change of permissions or times reports success and does nothing), nothing it was after may appear in what it prints, its own environment must hold none of the gateway's settings or secrets (only `COLUMBUS_RUN_DIR`), no file outside may change, in its contents, permissions or times, and nothing may connect; reading its inputs, importing the engine's packages, writing its temporary files and its outputs must still work, and the audit lines must name the rule. A second test checks that no script runs where the sandbox cannot be set up. The launcher's own rules on Linux are checked by `levels_a_and_b_on_linux_keep_the_system_and_other_processes_out` in [`tests/confine.rs`](../crates/gateway/tests/confine.rs).

Limits to know: what the assistant reads is sent to the AI service, and the boundary does not change that. Text hidden in data, documents or a tool's output can still mislead the assistant; it cannot use that to read beyond a source's rules, to change a source, or to send anything out without the person. The sandbox is the operating system's, with the known limits listed under [Confinement levels](#confinement-levels).

### Python environments

An **environment** is a Python interpreter the person registered, for `run_python` scripts that need libraries the engine doesn't have (build brief Part 5). The engine's Python stays the default, and environments run user code only. Personal tools and workflow steps can name one too (below), governed environments at level A only.

- **Policy (F-7, F-15).** `environments: { allow, allow_trusted, allow_network, index_hosts }` and `scripts: { approval, session_approval }`; every switch is off by default (`scripts.approval` is `each`), `index_hosts` defaults to `[pypi.org, files.pythonhosted.org]`, and unknown keys in these two sections are refused. `index_hosts` lists the package index hosts Columbus may reach when it creates an environment (below): `host` or `host:port`; the first is the index (`https://<host>/simple/`; a mirror on this computer, `127.0.0.1` or `localhost`, is reached over plain `http://`), the others may serve its files. While `environments.allow` is off, environments can't be registered, confirmed or proposed, `run_python`'s `environment` is refused, `whoami` lists none, and scripts run in the engine's Python as before. `allow_trusted` lets an environment be registered, confirmed and run as `trusted` (below), and is checked again at every run; `allow_network` lets a governed environment run at confinement level B. `scripts.approval` says when a level-A script asks the person: `each` run, once per `session`, or `none` ([Scripts](#the-boundary-d-16)); `scripts.session_approval: true` is the older spelling of `approval: session`.
- **The registration (F-4)**, `environments/<id>.yaml` beside the connections folder (`COLUMBUS_ENVIRONMENTS` overrides): `id` (`[a-z0-9-]{1,40}`, the file's name), `python` (absolute path to the interpreter), `trust` (`governed` or `trusted`), `confinement` (`A`, the default, or `B`; governed only), `created_by` (`person` or `columbus`), `description` (free text), `probe` (`{python_version, packages_sha256, arcpy, licence, probed_at}`, written by Columbus) and `confirmed_at` (ISO 8601). Unknown keys are refused. Environments Columbus creates live in `<Columbus data>/envs/<id>/` (`envs` beside the session workspaces; `COLUMBUS_ENVS` overrides).
- **Registering, at the keyboard only.** `columbus-mcp env add <id> --python <path> [--trust governed|trusted] [--confinement A|B] [--description TEXT]` refuses at once if policy doesn't allow it (`environments.allow`, `allow_trusted` for `--trust trusted`, `allow_network` for `--confinement B`), if the id is taken, or if the path isn't a Python interpreter (its file name must be `python`, `python3`, `python3.N` or `python.exe`, and it must answer the probe). It then probes the interpreter, shows what it found, and asks the person to type the id on the terminal itself (not stdin), as `servers approve` does. `columbus-mcp env confirm <id>` probes again and confirms the registration as its file stands now; `columbus-mcp env list` shows each one and its state. **In the app** (T-12, REQ-11), Settings › Python environments lists each registration with its state (Ready; "Changed: confirm it again" with why; or cannot be read), trust and confinement, Python version and arcpy line ("arcpy: yes (experimental); ArcGIS Pro licence: Advanced" or "arcpy: no"). **Add environment** takes the id, the interpreter's path (typed or chosen), trust (trusted only while `allow_trusted`), confinement (B only while `allow_network`) and a description; it refuses at once as the terminal does, probes the interpreter, then asks the person to confirm with Touch ID or the account password (macOS) or Windows Hello, as for a connection, the prompt naming the path, Python version, package count, arcpy line and trust; only then is it registered (`environments::register`, the id standing for the typed confirmation). **Confirm** (or **Confirm again**) probes again and confirms the file as it stands, the same way; **Remove** asks the same confirmation and says whether the folder goes too (only for one Columbus created). With no Touch ID or Windows Hello (Linux), the page says to use the terminal. No MCP tool registers, changes or confirms an environment, and no confined script can write the environments folder.
- **The probe (R-13)** runs the interpreter itself (never the gateway or engine) with `-I -B -X utf8`, no `COLUMBUS_*` settings, and a 120 s limit after which it and everything it started are stopped. It records the Python version; the SHA-256 of the sorted `name==version` lines `importlib.metadata` sees, followed, where `<prefix>/conda-meta/` exists, by its sorted file names; whether `arcpy` imports, and `arcpy.ProductInfo()`.
- **Creating one (REQ-14).** The assistant asks with `propose_environment` (an id, a Python version, exact-pinned packages and a reason). Refused at once: anything that isn't `name==version` (or `name[extra]==version`) with a valid package name and an exact public version (no ranges, wildcards, `===`, local versions, markers, URLs, paths or VCS links; a URL is refused naming its host), duplicates, more than 50 packages, an id already registered or whose folder exists, more than 20 proposals waiting, and everything while `environments.allow` is off. A proposal waits in `environments/.proposals/<id>.json`; filing it again replaces it. Nothing is downloaded until the person approves it at the keyboard: `columbus-mcp env proposals` lists them, `columbus-mcp env approve <id>` shows the reason, Python, packages, index hosts and destination and asks for the id typed on the terminal itself, `columbus-mcp env decline <id>` deletes one. Both go through one library function, `columbus_shared::env_create::approve`, bound to the fingerprint of what the person was shown (id, Python, packages, reason) and to their confirmation; the app's Settings › Python environments lists waiting proposals (packages, Python, why) with **Approve**, which calls it after Touch ID or Windows Hello with the fingerprint of the proposal the page showed (a proposal changed since is refused), and **Decline**, which needs no confirmation. No MCP tool approves one. On approval Columbus runs its own uv: the one installed in the engine from `workers/python/requirements-uv.txt` (uv 0.13.7, pinned by the SHA-256 of each wheel; the engine setup installs it; found with `uv.find_uv_bin()` in the engine, never on `PATH`). It makes a new folder `<Columbus data>/envs/<id>/` (refused if it exists) and creates a venv there with `uv venv` from a Python already on the computer: the engine's own when the version matches (or none was asked for), otherwise one uv finds locally; never a download (`UV_PYTHON_DOWNLOADS=never`, `--no-python-downloads`). It then installs into that venv only (`uv pip install --python <envs/id>/…/python`, after checking the folder's real path is under `envs/` and holds `pyvenv.cfg`), so it never installs into `arcgispro-py3`, a Pro clone or any registered environment. The install is wheels only (`--no-build`: no package's build code runs; a package without a wheel for this system is refused with "a package has no wheel for this system…"), with uv's configuration ignored (`--no-config`, `UV_NO_CONFIG=1`), a cleared environment (no `UV_*`, `PIP_*`, `VIRTUAL_ENV`, proxy or other settings of the person's; only what programs need to run, and `SSL_CERT_FILE`/`SSL_CERT_DIR`), no cache (`--no-cache`), the system's certificates (`--system-certs`), and the index `--default-index` built from the first of `index_hosts` (`--index-strategy first-index`). Every connection uv makes goes through a proxy Columbus runs on 127.0.0.1 for that creation only (`HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`), which lets through exactly the `index_hosts` (HTTPS on port 443 or the port given; plain HTTP only to a mirror on this computer), so redirects and file links to any other host are refused there, and the creation fails with "creating the environment needed <host>, which is not in environments.index_hosts…". When the computer itself has an `http://` `HTTPS_PROXY`, the proxy goes through it (except for `NO_PROXY` hosts). Columbus then checks every pinned package is installed at its version, probes the new interpreter and registers it governed, confinement A, `created_by: columbus`, confirmed (`description` "Created by Columbus: <reason>"); `whoami` lists it. On any failure the new folder is deleted, nothing is registered, and the proposal stays for the person to decline. Removing it later (`env remove`) deletes the folder too. Limits: dependencies of the pinned packages are resolved by uv from the same index (each from a wheel); uv's own network code honours the proxy settings, which is what the host rule rests on.
- **Confirmation and `changed` (R-13b).** Confirming records, apart from the YAML (in `environments/.confirmed.json`), a SHA-256 over `python`, `trust`, `confinement` and `created_by` with the `probe`, the interpreter's prefixes (the folders its scripts may read) and a freshness signal: the interpreter file's size and time and the names directly in each folder on its `sys.path` and in `conda-meta/`, bytecode caches left out. Any edit to those fields, or a changed signal (a package installed, removed or upgraded), marks the environment `changed`; so does the probe Columbus runs, confined, before every run, if the packages hash or Python version differ from the confirmed ones. A `changed` environment is refused with "…confirm it again in Settings" until the person confirms it again (`env confirm`), so editing the YAML can never make an environment trusted or point it at another interpreter unseen. An environment whose file doesn't load is `invalid`.
- **Governed runs (REQ-13).** `run_python` with `environment: <id>` runs only a `ready`, governed environment, through `columbus-confine` at its level: A (no network) or B (network, only while `environments.allow_network` is on; the approval card then says "the script can reach the internet"). It gets extracts only, exactly as engine scripts do: the run folder is the one place it can write, and the environment's own interpreter folders (its prefixes, as confirmed) are the only other folders it can read; on Windows each environment has its own AppContainer profile (`script.env-<id>`). At level A it follows `scripts.approval` like the engine's Python (with `none`, no approval); at level B every run is approved, whatever the key says. Where a card is shown it names the environment and its Python version, and the approval is bound to the environment's confirmed hash. Outputs are checked as layers by the engine, as before. Where an environment's interpreter cannot start confined on this system, its scripts are refused with a plain message and never run unconfined (A-1's fallback).
- **Trusted runs (D-3, REQ-15; experimental, D-13).** Only while `environments.allow_trusted` is on (off by default: a trusted environment is otherwise refused with "…organization policy does not allow trusted environments (environments.allow_trusted is off)"). The script runs unconfined, directly as the person, not through `columbus-confine`: it can read anything the person can, including `.sde` files and the network. This weakens the access rules by design (Security baseline item 1), and is the organization's choice. Every run is approved, wherever the person is asked; there is never an "allow for this session" (choosing it counts as once), and neither `scripts.approval: session` nor `none` ever applies to trusted environments (under `none` the card says "A script that runs outside the sandbox is approved every run."). The approval card names the environment as "trusted environment <id> (experimental)", with its arcpy licence line, and states exactly: "Columbus cannot enforce your connection rules for this run: the script can read, write and send data anywhere you can." (also in the card's detail as `warning`). It still gets the same run folder, copies of its inputs, time limit and output copying; at the time limit, and when it ends, everything it started and left running is ended (its process group on Unix; on Windows a job object of its own, which it is put in before it starts and which no process in it can leave); its environment is the person's own (arcpy's licence check needs it) without any `COLUMBUS_*` setting, with its temporary files in the run folder. Before each run its interpreter is probed, unconfined, for the confirmed packages, as governed ones are confined. Outputs that come back through Columbus carry every data label of the session and of its inputs plus `environment:<id>`, so later exports and flows through Columbus still follow the flow rules: an organization rule from `environment:*` (or the connection labels) to a folder asks for, or denies, an export of them. What the script does directly is outside Columbus's control. Trusted environments are never used by personal tools or workflow steps (below). arcpy is expected to need a trusted environment, because its licence check reads the person's profile and registry and, for Named User licences, the network (A-6, to be confirmed on a real Pro machine in H-2); running arcpy under the person's Pro licence is their organization's call (not legal advice).
- **arcpy and its licence (REQ-16; experimental, D-13).** The probe (registration and confirmation only, at the keyboard) imports `arcpy` inside the probed interpreter only, never in the gateway or the engine, and records `arcpy.ProductInfo()` as `probe.licence`. It is reported in plain words: `ArcInfo` "Advanced", `ArcEditor` "Standard", `ArcView` "Basic", `ArcServer` "ArcGIS Server (not an ArcGIS Pro licence)", `Engine` and `EngineGeoDB` likewise, `NotInitialized` "not initialized: open ArcGIS Pro and sign in; Named User licences lapse after about 14 days without Pro being opened", anything else "unrecognized (…)", and arcpy that imports without answering "unknown". `whoami` shows "ArcGIS Pro licence: Advanced" etc.; `env add` and `env confirm` show the same words before the person types the id. A new licence state (Pro opened and signed in) shows after `env confirm`. Approving a workflow whose step runs in a governed environment with arcpy shows it as a warning (below).
- **The probe's limit (R-13).** 120 s. A probe that runs longer is stopped with everything it started and reported ("the probe of … ran longer than 120 s and was stopped, with everything it started; nothing was recorded…"); nothing is registered or confirmed. Only test builds (debug assertions on) read `COLUMBUS_TEST_PROBE_SECONDS`, which can shorten it, never lengthen it; release builds never read it.
- **Audit and provenance.** A `run_python` audit line carries `environment` (F-8): the id, or `null` for the engine's Python. Its provenance step carries `environment` (F-9): `{id, trust, python_version, packages_sha256}`, or `null` for the engine, and the confinement level and network actually used (`{level: "none", unconfined: true, …}` for a trusted run). The audit line and provenance carry the run's data labels, `environment:<id>` included for a trusted run.
- **Session approval for scripts (REQ-17, R-15, AF-6).** Only while policy says `scripts.approval: session` (or the older `scripts.session_approval: true`, with no `approval` stated); off by default. The `run_python` card then offers **Allow this script for the session** (on the approvals page and in the AI app's own prompt; in the app's chat the button reads **Allow this script for this chat**; each with what it covers: "runs this exact code (sha256 …) in <the environment or the engine's Python> again with any inputs, without asking, until this chat or AI app connection ends; any change to the code asks again"), for the engine's Python and for governed environments at level A only. Choosing it allows that run and grants a standing approval bound to the SHA-256 of the exact code text, the environment's id and its confirmation hash (none for the engine), and the Columbus session: one chat in the app, or one MCP connection from another AI app, ending when that ends. The same code with other inputs (or another time limit) in the same session then runs without asking; one changed character, another environment, or a new session asks again. A trusted environment or a governed one at level B never offers it (the card says "Scripts are approved one run at a time", and choosing it on the page counts as once), nor does anything under `scripts.approval: each`. As every "allow for this session", it is withdrawn when the settings change. The audit line of a run it allowed records the approval as `standing`.
- **Personal tools and workflow steps (F-5, F-6, REQ-18).** A personal tool's `plugin.yaml` may name `environment: <id>`, a registered governed environment at confinement level A (no network), given to `propose_tool` as `environment`; without it the tool runs in the engine's Python. A workflow step that calls a personal tool may name its own `environment` (the default is the tool's); other steps may not name one. Only the id is stored, never a path. The tool runs through the plugin host with that environment's interpreter, confined at level A as every personal tool is; it can read the environment's interpreter folders (its prefixes as confirmed) instead of the engine's, under a confinement profile of its own per tool and environment. `run_tool` takes `environment` too, for personal tools only (workflow steps pass theirs through it). The environment is checked when the tool is proposed (before the person is asked; the test-run card names it, and the approval is bound to its confirmation hash), at the test run, and before every run: registered, `ready`, governed, level A, allowed by policy (`environments.allow`), and its interpreter probed confined for the confirmed packages, as for scripts. A tool or step whose environment is missing (removed), `changed`, invalid, trusted, at level B or no longer allowed stops with "needs you: the environment this tool runs in can't be used: …" and the reason (a changed one says "…confirm it again in Settings"). A trusted environment is refused for a tool or step whatever `allow_trusted` says: `propose_tool` and `propose_workflow` refuse one, and a run refuses it if the environment was re-registered as trusted later. In a workflow run (R-13c) such a step is recorded `needs_you`; the run goes on with the steps that don't use its result (a step that does is `skipped`), then ends `needs_you` without exporting, reviewing or emailing anything. Such a tool's describe check is made at each run, in its environment, rather than when it is loaded. Approving a workflow shows warnings (`warnings` in `propose_workflow`'s answer and in the app's view, and at the end of its plain-words account as "Warning: …"): for each step whose environment has arcpy, its licence line ("ArcGIS Pro licence: Advanced"), and for a step whose environment is missing, changed, trusted or at level B, that it will stop with "needs you". The audit line of a personal tool run carries `environment` (F-8; null for the engine), and its provenance step the `environment` map (F-9). Limit: a tool's code may still import only the modules the tool lint allows (an environment can supply one the engine lacks, such as `networkx` or `scipy`, or other versions), whatever else the environment holds.
- **`whoami`** reports `policy.environments_allowed`, `trusted_environments_allowed` and `environment_network_allowed`, and lists `environments`: `{id, trust, created_by, status (ready, changed or invalid), python_version, arcpy ("arcpy: no", or "arcpy: yes (experimental); ArcGIS Pro licence: Advanced"), licence ("ArcGIS Pro licence: …", or null without arcpy), trust_line (for trusted: "trusted (experimental): scripts run unconfined as the person, each run approved; …"), experimental (true for arcpy or trusted environments, D-13), confinement ("none" for trusted), description, reason}`.
- **Removing.** `columbus-mcp env remove <id>` shows what it deletes and asks for the id typed on the terminal. It deletes the YAML and its confirmation. Only an environment whose confirmed registration says `created_by: columbus`, and whose folder's real path is `<Columbus data>/envs/<id>/`, also loses that folder; a folder the person registered (a Pro clone, a venv) is never deleted. Past audit lines and provenance stay as they are.

**Edits.** GeoPackage and PostGIS datasets, in two steps. `propose_edits` reads the touched rows with the same checked SELECT as every read (the connection's row filter applied), refuses rows it does not return, fields hidden by policy or unknown, the key, the geometry column as a plain value, values of the wrong type, and invalid or wrongly typed geometry (GeoJSON, reprojected to the dataset's CRS); it saves the change set (with a fingerprint of each row as read) and a preview layer to the workspace. `apply_edits` with `target: "copy"` writes a new workspace layer and touches nothing else. With `target: "source"` it needs organization policy's `allow_edits: true`, a connection whose effective mode is `read-write`, an unchanged change set (SHA-256) made in this session, and the person's approval of that exact change set, every time (the card lists each change). The write is one transaction: each touched row is read again, locked where the database can, and must match its fingerprint; each statement is limited to its key and the row filter and must touch exactly one row; each row written must still be inside the row filter afterwards; values travel only as query parameters. Anything else rolls everything back. A change set is used once; the audit log and provenance record the approval, the counts and the change set's hash. Oracle, SQL Server and Esri geodatabases are refused for now.

**Hidden fields and row filters.** The server rewrites every table a query reads into a filtered derived table that contains only the fields the policy does not hide: `FROM (SELECT <visible fields> FROM t WHERE <row filter> OFFSET 0) t`. Whatever the query does (`SELECT *`, UNION, column alias lists, `USING`/`NATURAL` joins, whole-row values like `to_jsonb(t)`), a hidden field is simply not there to reach. Each table name (with or without hidden fields) is resolved to exactly one listed table, and the allow and deny lists and row filters apply to that table, not to how the query spelled it by the database's own rules (quoted names exact, unquoted folded), and the rewritten query names that table in full, so the database cannot pick a different one; ambiguous or unlisted names are refused. Columns are always listed by name, so a column added after the list was taken (it is refreshed every five minutes) stays out until it has been seen. A query that names one is refused with a clear message. The `OFFSET 0` keeps the database from merging the filtered table into the outer query, so the caller's conditions only ever run on rows the row filter allows: an error raised by a condition cannot describe a row outside it. Each dialect has its own barrier: `LIMIT -1 OFFSET 0` on SQLite; `AND ROWNUM > 0` inside the filtered table's WHERE on Oracle (a view that uses ROWNUM can be neither merged nor have predicates pushed into it; the `NO_MERGE` hint stops merging only, and Oracle would still push the caller's WHERE in beside the row filter); `TOP (9223372036854775807)` on SQL Server (a filter cannot move below a TOP without changing its result), where a failed conversion would otherwise quote the value ("Conversion failed when converting the varchar value '…'"). Database errors keep only their primary message, with quoted values removed unless the error is about a name in the query. Files in the workspace are fingerprinted when Columbus writes them, and the GIS tools refuse a file whose content has changed since.

**Results.** At most 500 rows go back to the AI provider per call (organization policy can lower this). Larger results are written to the session workspace and the path returned. Fields matching the policy's `hide_fields` are stripped before anything leaves the server.

**Limits and large tables.** Each query reads at most 200,000 rows and each call runs at most 120 seconds by default. Organization policy can lower either; it can raise them only with an explicit opt-in, `limits: { rows: 2000000, seconds: 900, allow_raise: true }`, and never past a ceiling fixed in code (20,000,000 rows, 3,600 seconds). A value above a default without `allow_raise` is ignored (the default applies) and `whoami` says so. Connections and data groups can still only lower what the organization allows. Every tool takes its limits from the same two functions (the organization's limits, narrowed by the connection), so `query_features`, `sql_select` and its row-limit sentinel, `vector_op`, `raster_op`'s pixel limit, `registry_fetch`, engine plugin extracts, `run_python`'s time cap, edits, notes, exports and connected-server calls agree; `whoami` and `describe_connection` report the values in force. A settings change that lowers them applies from the next call and withholds the answer of a call running across it, as before. Large results are written as they arrive: the engines fetch rows from the database 2,000 at a time and hand them on, `sql_select` streams them into its CSV, plugin extracts into their SQLite file, and `query_features` builds results of up to 100,000 rows in memory as before and writes anything larger to its GeoPackage (or CSV) in batches of 20,000, so memory does not grow with the rows read (check `query.streamed`). The streamed GeoPackage is written with SQLite directly: the GeoPackage tables, then features in batches; a column's type is the widest its values needed (a column that held only integers in the first batch and a real later is rebuilt as real at the end, in SQLite, so no value is cut), and the source's own `fid` column, if any, is kept as `source_fid`. It has no spatial index. Row counts, the CRS and geometry checks are counted batch by batch, and a result cut off at the limit is still reported (`query.read_limit`) and marked truncated, which follows it into everything built from it. `read_output` reads a large layer a page at a time. GIS operations (`vector_op`, `verify`, the map) still load a layer whole, so on millions of rows filter and aggregate first, in the source or in a project database.

**Project databases.** `project_db` gives the assistant a local database for a project: it pulls tables with `query_features` or `sql_select` (filtered and aggregated in the source first), loads them, adds primary and foreign keys, indexes, views and comments, and joins them with SQL. It writes only its own file; source databases stay read-only, behind the same checks as every read.

- *Engine.* DuckDB, because it joins and aggregates millions of rows quickly in little memory (spilling to disk past `project_db.memory_mb`, 2,048 MB by default) and has wheels for Windows x64, macOS arm64 and Linux. Its spatial extension usually downloads at run time, which Columbus never allows; the engine instead installs it beside DuckDB from `duckdb-extension-spatial` (a community package that carries DuckDB Labs' own signed extension binary), and DuckDB checks the binary's signature when it loads. Both come from [`requirements-projectdb.txt`](../workers/python/requirements-projectdb.txt) (with `pytz`, pure Python, which DuckDB needs to return timestamps with a time zone such as `now()`), pinned by version and by the SHA-256 of every wheel (Windows x64, macOS arm64 and Linux x64, CPython 3.12 and 3.13) and installed on their own with `--require-hashes --no-deps --only-binary :all:` (the setup scripts, pixi's `project-db` task and CI all do this), so no other build of either, and nothing they might depend on, can be substituted. Columbus never imports the extension's package, so its `__init__.py` never runs: the worker and the setup scripts find the extension file with `importlib.util.find_spec`, which does not execute it. (Downloading the file from extensions.duckdb.org against a pinned hash at setup would remove the community package entirely, but needs a download step in the offline installs; the hash-pinned wheel gives the same guarantee for the bytes installed.) Geometry is stored in DuckDB's built-in `GEOMETRY` type, so a database opens and its geometry comes out even where the extension is missing; only the spatial SQL functions are then unavailable (`create` says so). We chose this over SQLite/GeoPackage, which every GIS opens directly, because a project database is for joins and aggregation over many large tables, where DuckDB is much faster; its results come out as GeoPackage layers anyway.
- *Where.* `scope: session` puts it in the session workspace (`projectdb/<name>/`); `scope: project` in a named folder under the workspaces root (`projects/<name>/`), kept for later sessions. The gateway resolves the folder itself, never from a path the assistant gives, walking it without following links.
- *What goes in.* Only workspace layers a Columbus tool, approved plugin or approved script wrote in this session, unchanged since (never a connected server's file). They already leave hidden fields out; the load drops any column the policy hides anyway, and the gateway checks the loaded columns again. A load is one transaction, streamed in batches; a declared primary key refuses duplicates and nulls. CSV columns become numbers only where every value reads back exactly as written, so zero-padded codes stay text; the types are worked out in a first pass over the file, before anything is inserted, so the table is created with its final types and filled once (`types: text` keeps every column as text). Appending to a table keeps its types.
- *What runs.* Every connection is opened with the spatial extension loaded from its file, then locked: `enable_external_access = false` (no other file or URL, no `ATTACH`, `COPY`, `EXPORT`, `INSTALL` or `LOAD`), Python replacement scans off, extension autoloading and autoinstalling off, persistent secrets off, and `lock_configuration = true`, so no statement can change any of it. Statements are parsed by DuckDB itself on that locked connection (parsing `IMPORT DATABASE` reads files, so it never happens on an unlocked one) and allowed by kind: CREATE (tables, views, indexes, sequences, macros, schemas, types; never secrets), INSERT, UPDATE, DELETE, MERGE, ALTER (including COMMENT ON), DROP, ANALYZE and VACUUM for `execute`; one SELECT (or DESCRIBE, SUMMARIZE, SHOW, EXPLAIN) for `query`. Functions that read files, other databases, settings or logs, or run SQL given as text or as a serialized plan (`read_*`, `*_scan`, `glob`, `ST_Read*`, `query`, `query_table`, `json_execute_serialized_sql`, `json_deserialize_sql`, `current_setting`, `checkpoint` and others) are refused by name too, as are built-in views and table functions that show settings, paths, logs, databases or memory even without a call (`pg_settings`, `duckdb_databases`, `duckdb_settings`, `pragma_*`, `duckdb_logs`, `pg_prepared_statements`, schema-qualified or not), with names found by DuckDB's own tokenizer (its byte offsets mapped to characters, so non-ASCII text such as "Peñasco" cannot shift them), so string literals (`E'…'` escapes and `$$` quotes included), comments and quoted names are read as DuckDB reads them; a statement the tokenizer does not read to its end is refused. An `execute` batch is one transaction: all of it or none. Each statement reports how many rows it changed, from DuckDB's own count, never from a value; `RETURNING` (which sends stored values back) is refused in INSERT, UPDATE, DELETE and MERGE. DuckDB runs `ALTER TABLE … ADD COLUMN … DEFAULT <expression>` (anything but a constant, such as `DEFAULT false` on most types, `DEFAULT current_date` or `DEFAULT 1+1`) as several statements of its own, which the locked connection cannot run; Columbus runs it as the three plain statements it stands for, each checked like any other: add the column, set its default, fill it with an UPDATE. DuckDB cannot ALTER a table after changing its rows in the same transaction, so the fills of a run of ALTER statements wait until the run ends; an ALTER after an UPDATE of the same table in one batch fails at COMMIT, and the error says to put the ALTER statements first or give them their own call. `ADD COLUMN IF NOT EXISTS … DEFAULT <expression>` is refused with that workaround. `execute` reports the tables there afterwards and those dropped or dropped and made again, and the gateway takes their load records out after merging the record on disk, so another session's copy cannot bring them back. `query` and `describe` open the database read-only in DuckDB itself, so nothing they run can change it (an `EXPLAIN ANALYZE DELETE …` runs what it explains; it is refused by name, since EXPLAIN may only wrap a SELECT, and the read-only connection refuses it anyway). `error()` and DuckDB's logging functions are refused too. Error messages can carry stored values (a conversion, key, range or JSON error prints the value that failed), so they are scrubbed, not trusted: only the first line is kept; for errors other than parser, binder, catalog, syntax and permission errors (which name things in the statement), everything from the first quote to the last is cut out and every number is replaced with `#`; an invalid-input error with no quotes says only its class. This narrows what an error can carry; it does not make errors a safe channel, which is why any action that opens a database labels the session first (below). Every action passes every error through this, at COMMIT too (a unique index checked at commit names the duplicate value), and anything that is not a DuckDB error says only its class. When the session may not see rows at all (`return_rows: 0`), errors say only their class, a PIVOT without an IN list and an ENUM built from a query are refused (both would turn stored values into names), and query results leave out their extent and every check's detail (coordinates are stored values), and a check whose message counts or measures stored values (invalid or empty geometries) says only that there are some; CRS check messages never hold coordinates at any `return_rows` (the extent is in the detail). ENUM types are shown as `ENUM`, never with their values. Row counts and timing still say something about the data; with `return_rows: 0` treat them as a side channel, not as nothing. Each call is interrupted at the time limit. One action at a time runs on a database in a session.
- *Size.* `project_db.max_mb` (default 20,480 MB) caps each database. What counts is what the database would take if the call committed: its used blocks (an open transaction's included, so space freed by DROP and filled again counts), the data the transaction still holds in memory (counted at its in-memory size, more than it takes compressed, so a large single statement can be refused somewhat before the file would reach the cap: new rows, the rows an UPDATE rewrites, an index being built; only their growth during the call counts), and the spill folder. Loads insert one row group (122,880 rows) at a time, so DuckDB writes each batch compressed as it goes and at most about one batch waits in memory; in our tests a single load into an empty database needed a cap of about 1.4–1.5 times the size it ends up taking (an 800,000-row parcel GeoPackage taking 142 MB loaded under a 207 MB cap; the same table's 17 MB CSV under 24 MB), so the largest single load under a cap is about two thirds of it, less what the database already holds. A watcher on a second connection checks this four times a second and interrupts the call, which rolls it back; before COMMIT the watcher and the time limit are stopped (so nothing can interrupt the commit itself) and the total is checked once more, so a call too short to be watched, or an interrupt that arrived between two statements, is caught there. A batch that only frees space (DROP, DELETE, VACUUM, ANALYZE) is stopped only if it grows the database well beyond where it started; a read-only `query` is held only to its spill folder. DuckDB's own `max_temp_directory_size` is set from the cap as well, but DuckDB 1.5.5 does not hold to it. Before a `load` or `execute`, what the database holds (its used blocks and log) is checked: over the cap, `load` and every statement but DROP, DELETE, VACUUM and ANALYZE are refused. DROP TABLE frees its space for reuse inside the file; DELETE frees little, and the file itself never shrinks (delete the database to get the disk back). Each load and execute reports the size after its commit (`used_bytes`: the used blocks and log, measured on the closed file; `bytes`: the file and its log on disk, which can be larger, since space freed or rolled back stays in the file for reuse) as `project_db.size`, a warning once over the cap. Disk use is bounded but can pass the cap: space a refused or rolled-back call used stays in the file and is reused by later calls, so the file can reach roughly the cap plus one call's overshoot (in our tests up to about 2–3 times a small cap, levelling off however many calls were refused). Rewriting a whole column of a large table with UPDATE is counted at several times its final growth, so such an UPDATE can be refused well under the cap: build a new table with CREATE TABLE AS instead. Each connection spills to its own folder under `<database>.tmp`, and spill left by a call that was killed is cleared the next time the database is opened for writing.
- *Labels.* The gateway keeps a record beside the file (`columbus-project.json`), outside the SQL's reach: the union of the data labels of everything loaded, what each connection allowed when its data came in, the fields hidden at every load, and each table's source, provenance, CRS and truncation. Any action that opens the database labels the session with its labels first (a failed statement's error comes from the data too), and every result carries them, so flow rules and export rules apply to what comes out. A settings change during a session that narrows any of its connections, or hides a new field, deletes the project databases the session has used, as it deletes workspace files with that data. Any other database (kept from an earlier session, not opened in this one) whose connections have changed since its data came in, or whose data may hold a field now hidden, is withheld when next used: every action but `delete` and `list` is refused. The record is re-read after each call and merged on every write (labels, tables, fails, truncation), under a lock file so two sessions never interleave; labels another session added meanwhile reach this session and its answer, the merged record is checked again, and two sessions that loaded the same connection under different settings withhold the database. A database file found without its record is withheld too (never given a fresh record without labels). Sessions have no project scope or data groups of their own yet; when they do, the check must cover them too.
- *Approvals and exports.* Writing the person's own project database needs no approval, so the assistant batches its statements into one `execute`. Deleting a whole database asks the person every time. Nothing leaves it except through `query`, whose result is an ordinary workspace layer: a table loaded from a cut-off result marks it truncated, fails from the loaded layers' history carry over, and `export_output` applies its usual checks and approvals.
- *Audit.* Every action is an audit line; every statement of an `execute` has its own (its kind, its own hash and the rows it changed; never its text, which may hold values). A refused or failed batch is one line saying which statement and why. Provenance records the full SQL.
- *Limits.* Results from `query` are capped by the organization's read limit and report `query.read_limit`. The person's other programs can open and change the file (as with any file in their profile); Columbus's record of what it holds is only as trustworthy as that profile. DuckDB holds a lock while a call has the file open, so two sessions use one project database in turn.

## Engine plugins

GIS tools that touch an organization's data are written as **engine plugins**: a folder with a `plugin.yaml` and a worker built on the Columbus plugin SDK, for Python ([`workers/python/columbus_plugin`](../workers/python/columbus_plugin)) or Rust ([`workers/sdk-rust`](../workers/sdk-rust)). They speak [worker protocol v2](worker-protocol.md), the same protocol Columbus's own engine now uses. Typed parameters tell the gateway what each argument is, so it governs them argument by argument:

- A **dataset** argument (`"lrs:events"`, or `{connection, dataset, where}`) is read by the gateway through that connection's permissions, row filter and hidden fields, and handed to the plugin as a read-only extract. Plugins never receive credentials, and never a dataset cut off at the read limit.
- Outputs go only to workspace paths the gateway assigns, and carry the inputs' data labels, so Rule 3 follows them.
- A plugin runs only after a person approves its exact contents (`columbus-mcp plugins approve <id>`); any change to `plugin.yaml` or the worker switches it off (the files are checked again before every start and restart of its worker), and a worker whose own description differs from its `plugin.yaml` is refused.
- Each run's folder (its copies of the inputs, its outputs) is deleted once the outputs are copied out, however the run ends. An organization plugin's worker lives across runs and can keep data in memory or in its own folder from one run to the next, so its outputs carry the data labels of every input it has had in the session, not only this run's.

The Rust SDK's [`geometry_stats`](../workers/sdk-rust/examples/geometry_stats.rs) example reads governed geometry (GeoPackage or PostGIS) and reports extents and validity. [`examples/plugins/lrs-check`](../examples/plugins/lrs-check) is the LRS event checker from design change 1, implemented: gaps, overlaps, reversed and out-of-range measures, and events on unknown routes, with a findings layer and a report table. Agents call plugin tools through `run_tool` as `<plugin id>.<tool>`, for example `contoso.lrs-check.check_events`. A tool's manifest can describe it for the assistants that call it (title, description, when not to use it, what each input must be: geometry, CRS, fields; units; outputs and their CRS; the checks it reports; examples), and `describe_tool` shows all of it; outputs Columbus can read as layers (GeoPackage, CSV) are checked as layers after each run, and their fails go with them ([plugin.yaml](worker-protocol.md#pluginyaml)).

## Personal tools

A script that keeps being useful (finding measures along routes, checking event gaps) can become one of the person's own tools: the person says "add the script we just made as a tool", the assistant packages it with `propose_tool`, the person installs it, and from then on any assistant working through Columbus finds it with `search_tools` and runs it with `run_tool` as `personal.<name>.run`, with no approval per run. Personal tools are engine plugins, with the rules below on top. The assistant follows [designing-tools.md](../skills/working-with-columbus/references/designing-tools.md) in the skills library; [examples/tools](../examples/tools) holds the LRS examples.

**Proposing.** `propose_tool` takes the tool's name, title, description and when not to use it; typed inputs (workspace layers or tables, each with its geometry type, the CRS it must be in and the fields it reads), scalar parameters (types, units for every number, defaults, ranges, allowed values), outputs (layer, table or report, with geometry and CRS), the checks it reports, examples, the code (a `run(ctx)` function) and a test on this session's layers. The server checks it all and refuses with the full list of problems:

- The manifest is strict: unknown fields are refused, names are checked, numbers need units, layers need geometry and CRS, and every text field is trimmed and plain (no hidden, right-to-left, variation-selector or line-separator characters; short fields one line; the title without quotes). The title and descriptions other assistants will read are checked like a connected server's tool descriptions: wording aimed at the model ("ignore previous", "do not tell the user"), URLs and e-mail addresses, and mentions of credentials are refused.
- The code must read as it runs: plain text (the same character rules, lines of at most 200 characters, no more than 5 blank lines in a row), names in plain ASCII (Python folds look-alike letters into ASCII, so the check reads the source, not the parsed tree), each top-level name, `run` above all, bound once and never rebound, and a top level that holds only a docstring, imports, functions, classes and names given plain values (no calls, loops or conditions; plain defaults and annotations; no decorator on `run`, a short allow-list elsewhere; no metaclasses), no Python special attributes (`__code__`, `__globals__`...), `getattr`/`setattr`, `sys.modules`, frames or `inspect`, at most 2,000 lines and 40 comment lines in a row. A coding declaration (`# coding: utf-7` would let a comment decode into code) or a byte-order mark is refused, for scripts too, and both scripts and tools are run by compiling their UTF-8 text, where such a line does nothing. The person sees it with line numbers, on the approval card and on the app's Tools page.
- The code is parsed by the engine (never run to check it): no network or cloud modules, subprocesses, native code, dynamic imports or `eval`, no environment variables or credential stores, no strings that look like keys or passwords, no absolute paths, URLs or GDAL virtual file systems; `run(ctx)` must exist, and every input, parameter, output and check the code names must be declared, and every declared input and output used. These checks catch a tool that plainly tries; the sandbox is what stops one that does not.
- The test run is approved by the person (the card shows the whole `tool.py` and the manifest; every time, whatever `scripts.approval` says, with no "allow for this session": a new tool is something being installed), and runs exactly as an installed tool will: the plugin host, confined at level A, on copies of the named layers. A test that fails files nothing.

Then the proposal is filed in the person's tools folder (`tools/proposals/<id>/` beside the session workspaces, or under `COLUMBUS_TOOLS`): `plugin.yaml`, `tool.py` (the assistant's code followed by the few lines Columbus adds to serve `run` with the Python SDK) and a record of the test run that holds counts and check ids only, never the data. At most 20 wait at once; a new proposal of the same tool replaces the waiting one.

**Installing is the person's, never the assistant's.** A new tool permanently adds to what the assistant can run without asking, so it is confirmed outside the assistant's control: on the Columbus app's **Tools** page, the person reads the title, description, test run, warnings and the full manifest and code, and installs it with Touch ID or the account password on macOS, or Windows Hello on Windows (or declines it). The app installs exactly the files whose hash it showed, read again and checked after the confirmation, into `tools/<id>/`, and records that hash in `tools/approved.yaml`. On a machine without either, `columbus-mcp tools install ID` does the same after the person types the tool's id on the terminal itself (not stdin), as `plugins approve` does. No MCP tool writes to the tools folder except to file a proposal.

**Running.** An installed tool runs only while `approved.yaml` holds the hash of exactly its `plugin.yaml` and `tool.py`: any change to either switches it off ("changed since the person installed it") until it is proposed and installed again, so a code change is always a new proposal and a new install. It has one tool, `run`, with risk `read`; it takes workspace layers and tables (files a Columbus tool, an approved plugin or an approved script wrote in this session, unchanged; never a connected server's file, never a connection's dataset directly) and scalars, checked against its manifest. It runs through the plugin host confined at level A (no network; memory and processes capped; PROJ networking and GDAL's VRT drivers off), never unconfined whatever `allow_unconfined_local` says; level A must be among `plugins.levels`. Each run gets a new worker process of its own, started from a copy Columbus makes of exactly the installed `plugin.yaml` and `tool.py` after checking their hash on the very bytes it copies, so what runs is what was installed; personal tools run one at a time in a session (as scripts do). The worker can read that copy, the Python installation and the copies of this run's inputs in its own folder, and write only that folder; the folder is emptied before the run and deleted after it, inputs and all, and the worker is stopped, however the run ends, so nothing of one run (another layer, another connection's data) is there for the next. A proposal's test run works the same way, in a folder of its own that never meets the installed tool's. Its outputs are copied out without following links, carry the inputs' and session's data labels and fails, are checked as layers, and are recorded with provenance (the tool's hash, the inputs, the parameters). `list_providers` shows each one as kind `personal`. A tool whose `plugin.yaml` names an `environment` runs in that registered environment instead of the engine's Python, under the same rules ([Python environments](#python-environments)).

**Live, without a restart.** Organization plugins are set up when a session starts (a change to `plugins` in policy stops the session until a restart). Personal tools are read again whenever their folder changes, at every call as the settings files are: installing one makes it available from the next call of every running session, and removing one, a changed file or the policy switch going off takes it away from the next call. That is safe because each tool stands alone: one provider that only reads the files it is given and writes its own outputs, under its own approval hash; adding it changes nothing else, and nothing an approval was given for. A run already going when its tool is removed finishes.

**Policy.** `allow_personal_tools: true` turns them on (off by default, like scripts); off hides every installed tool at once and refuses `propose_tool`, and the app will not install one. Proposing also needs `allow_scripts: true`, since the test run runs the assistant's code as a script does; installed tools run without it. The person can turn it on in the app (Settings › Organization rules, or on the Tools page), confirmed like the other switches, unless the policy file is managed by IT. `deny_tools: [propose_tool]` keeps installed tools but stops new proposals; a tool's own name (`personal.locate-measures.run`) can be denied like any tool, which also hides it from `search_tools` and `list_providers`.

**Known limits.** An agent that can run programs as the person (a coding agent with a shell) can write the tools folder and `approved.yaml` itself, as it could the policy, connections or plugin approvals: give such agents only read-only database logins. The code checks are a second line of defence; the confinement is the boundary, with the same known limits as scripts (above, under Confinement levels). An installed tool is trusted to compute what it says: its checks and test run help, but the person's reading of the code is the review.

### Workflows

Jobs the person wants run again without waiting for them: the assistant proposes one with `propose_workflow` (a `workflow.yaml`: steps, the connections it reads, a schedule, an export folder for results), the person reads it in plain words and in full in the Columbus app (Workflows) and approves it with Touch ID or Windows Hello, and `columbus-mcp workflow run <id>` runs it: on its schedule (a launchd agent on macOS, a Task Scheduler task on Windows, made by the app), or with **Run now**.

- **Approval binds exactly what was shown:** the fingerprint covers `workflow.yaml` and the installed hash of every personal tool it uses. Any change to either is off until approved again.
- **A run does only what it lists.** Steps are reading and checking tools (`list_datasets`, `describe_dataset`, `sample_rows`, `query_features`, `sql_select`, `vector_op`, `raster_op`, `verify`, `read_output`) or installed personal tools; never scripts, edits, downloads or connected servers. Steps read every connection type through the same tools and rules as a chat, `files` folders and `arcgis` services included (REQ-25; `sql_select` stays refused on `arcgis`). The session's project scope is the workflow's connections: a step on a connection not in `scope.connections` is refused when proposed and again when it runs. References between steps never fill what is read or where results go.
- **Delivering results (F-11).** `outputs.folder: {export, steps, format}` exports each listed step's layer to the export folder; `format` is `gpkg` (default), `gdb`, `geojson`, `fgb`, `shp`, `csv` or `tif` (raster results), through the same export writers and rules as `export_output`. Files are named `<workflow>-<step>-<run>`; for `gdb` every character other than a letter or digit becomes `_` (`weekly_reach_assets_2026_11_09T06_00_00_000_1a2b.gdb`, one feature class of that name), since a feature class name is a letter then letters, digits and `_`. A new file geodatabase is made each run; an existing one of the name is never replaced.
- **ArcGIS sign-in across unattended runs (R-19, REQ-26).** Before a step uses a signed-in `arcgis` connection, if fewer than 7 days of its refresh token's life remain, or that is not known, the gateway swaps it for a new one (`grant_type=exchange_refresh_token`, redirect `urn:ietf:wg:oauth:2.0:oob`) and stores it, so a weekly workflow keeps its sign-in alive. The step's checks then include `arcgis.signin_renewed` (info). A renewal that can't be made for another reason (the portal does not answer) is a warning, `arcgis.signin_not_renewed`, and the step goes on; the next run tries again. A sign-in that has lapsed (by the record, or refused by the portal), was never made, or is for another portal stops the step with exactly "needs you: sign in again (columbus-mcp arcgis signin <id>)", naming the connection; the run ends `needs_you`, its report gives that line and the reason "Step <step> stopped: …", and nothing is exported. No token appears in the run record, report, audit log or provenance.
- **A run never waits for a person.** Any call that would need an approval is refused at once ("needs you") and the run stops there; an export to a folder that isn't `granted` is such a call. A personal tool step whose environment can't be used (missing, `changed`, trusted, at level B or no longer allowed) also stops with "needs you", but the run goes on with the steps that don't use its result, and then ends `needs_you` without exporting ([Python environments](#python-environments)).
- **Environments:** a personal tool step runs in its tool's environment, or in the one the step names (`environment: <id>`, F-6, personal tool steps only); approving shows the arcpy licence of each such environment that has arcpy as a warning.
- **Records:** each run writes `run.json` and a Markdown report under `workflows/runs/<id>/`; its calls are in the audit log as client `columbus-runner`. Runs are kept per `keep_runs` (with their workspaces).
- **Email (if the organization sets it up).** `outputs.email: {to: [addresses], when: always|problems, attach: true|false}` emails the run's report once the run has ended. The policy's `email` section names the mail server (`smtp_host`, `smtp_port`, `security`: `starttls` (default) or `tls`, never plain), `from`, an optional `username` (its password saved from the app's Workflows page, Email, into the credential store as `columbus.email-smtp`), the `allowed_domains` addresses must be in (exact domains), and whether a report may carry the files the run exported (`attachments`, off by default; `max_attachment_mb`, default 10). Addresses are checked when the workflow is proposed and again at every run against the policy in force then. Only files the run already exported through the export rules are attached. The organization's flow rules apply to email as to any destination, named `email:<domain>` (a `"*"` rule covers it): data the run read can't be emailed where a rule denies it or asks for approval each time (a run can't ask); otherwise approving the workflow, which names the addresses, is the approval. The report can quote rows through the AI review's notes, and the approval says so. Each email is audited as `email_report` before it is sent (with the data labels and the hash of the body) and after (who the mail server took); the report and `run.json` say whether it was sent. `whoami` shows `workflow_email` (the allowed domains). Sharing a workflow never shares whom it emails.
- **Opening a run's results in a chat (AF-19, REQ-27, R-20).** `run.json` records `scope` (the connections the workflow read) and `outputs`: for each step's layer, its file in the run's workspace, its SHA-256 (as the session recorded it when writing it), rows, `made_by`, source, labels, truncation, inherited fails, and its provenance record's id and SHA-256. A finished run's report page has **Open in a chat** (when it has outputs); `columbus-mcp workflow open <id> <run>` serves MCP over stdio the same way (for another AI app), and the app starts its chat with `COLUMBUS_OPEN_RUN=<id>/<run>`. Before serving anything the session checks the run has finished and that every output and its provenance file are byte-for-byte what the run wrote, inside a run workspace directly in the workspaces folder; otherwise it refuses to start, naming the file ("the run's output … (step …) changed on disk since the run, so the run can't be opened; run the workflow again"; the app checks first so the chat shows this). A run from before this record refuses with "run the workflow again". It then copies each output into its own `results/` as `<workflow>-<step>.<ext>` (re-hashing the copied bytes), records it with the run's rows, source, truncation and inherited fails, gives it the run's data labels (on the file and the session), and writes a new provenance record (`steps: open_run`, the run's `run_provenance`, its checks, `sha256`). The session's scope is the workflow's (narrowed by a project's, if one is also set). `whoami` returns `opened_run` (workflow, run, status, layers with handle, rows, labels, fingerprint and provenance, the run's exports, and its report, up to 20,000 characters), and the app's chat puts the layers and the report in the assistant's system prompt. All of the run's layers draw on the chat's map at once; the table shows them. The run is never changed: the chat never opens the run's files (handles of the run's session are refused as another session's), `export_output` refuses any export whose folder and name are one of the run's deliveries, whatever `overwrite` or approval, and filters, edits and exports make new outputs under the usual rules (flow rules apply through the labels; a folder that isn't granted asks).
- **Policy:** `allow_workflows: true` turns them on (off by default); off stops every installed one at once and refuses `propose_workflow`.
- **The optional AI review** sends a capped number of result rows (only the fields the workflow names) and its criteria to Anthropic with the person's API key; the model has no tools. Approving the workflow, whose description says what is sent and to whom, is the person's approval for it. The organization controls it as a tool, `workflow_review` (`deny_tools`, or leave it off a `tools` allowlist), and as a flow destination, `ai:anthropic` (a `flows` rule to `ai:*`, `server:*` or `*` covers it). A rule that denies, or that asks for an approval each time, refuses a workflow with a review when it is proposed, and stops the review (but not the rest of the run) if the rule is added later. The audit log records each review: who, model, rows sent, labels, never the rows.
- **Time limit:** a run stops at `run_minutes`; if anything blocks past that and two minutes more, the run is recorded as stopped at its limit (naming the step that was running), its engine processes are ended and it exits.

### Sharing tools and workflows

A person can send a coworker one of their installed tools, or an approved workflow with the tools it uses, as a `.columbus` file (**Share…** on the Tools page, or in the **⋯** menu of a workflow's page). The coworker opens it in their app (**Open a shared one** on Workflows, or **Open a shared file…** on the Tools page), and what it holds is filed as proposals, waiting for them exactly as their own assistant's do: they read every line and approve each with their own Touch ID or Windows Hello. Opening a file installs and runs nothing.

- **What travels:** the tool's `plugin.yaml` and `tool.py` (as installed, with their hash), or the workflow's `workflow.yaml` without its schedule plus every personal tool it uses; the sharer's sign-in name and when. A tool or step that runs in an environment carries only the environment's id (`environment: pro`), never its interpreter's path: it runs in the recipient's own environment of that name, which they register themselves (the import warns when they have no governed, ready one by that name; until then it stops with "needs you"). No rows, outputs, run reports, connection details or passwords; but a workflow's text holds what it was written with (dataset and connection names, `where` and `sql` text, its AI review criteria), and a tool's examples, so read before you share. Who shared a file is the file's own word: the app says so, and shows the file's name and where it is.
- **A shared tool is checked as a proposed one:** it must be exactly what `propose_tool` builds from its own files (every rule on names, descriptions and wording addressed to an assistant), its code must pass the same lint, and the policy must allow it (`deny_tools`, an organization plugin's id). It isn't test-run on the recipient's computer, since no data comes with it, and the app says so.
- **A shared workflow is rewritten to the recipient's names:** they choose which of their connections stands for each one it names (in its scope, its steps' `connection`, and datasets named in `vector_op`/`raster_op` inputs and `verify`'s layer, which must also be in its scope), and their export folder, with nothing chosen for them; it then passes the same checks as `propose_workflow`, and can be approved once its tools are installed. Its AI review criteria travel with it, shown for the recipient to read.
- **All or nothing:** everything in a file is checked before any of it is filed, the limits on waiting proposals included, and what was filed is taken back if filing fails part way. A tool or workflow already waiting for the person is never replaced: they decide on it first.
- **Policy:** `allow_shared_tools: true` lets the person open shared files (off by default; personal tools and workflows must be on too, and `propose_tool` and `propose_workflow` allowed, as for the assistant's). `deny_tools: [share_import]` turns opening off. Unlike `propose_tool`, opening a shared tool doesn't need `allow_scripts`, since nothing is test-run: an organization with scripts off that wants no new tool code at all leaves `allow_shared_tools` off. The app can turn it on, confirmed like the other switches. Every opening, refused ones included, is in the audit log as `share_import` (client `columbus-app-share`) with the file's hash, who it says it is from and the hash of each part, written before anything is filed. The CLI is `columbus-mcp share import '{"file": "...", "sha256": "...", "connections": {"theirs": "mine"}, "export": "..."}'` (`sha256`, the file's hash when the person was shown it, refuses a file that changed since).

**Signed shared files, the team library, and tools for everyone.**
- **Signing.** Share signs the file with the person's own sharing key (Ed25519, made the first time they share and kept in the system keychain; on Linux, where Columbus has no keychain, files go unsigned). The signature covers the whole file. Opening a file shows who signed it only as the key's fingerprint (32 hex digits), until the person trusts that key under a name (one name, one key: a name already given to another key, theirs or the organization's, is refused) ("Trust this sender": only after the sender reads them the same fingerprint; Tools › Team library › Show my sharing key). Trusted keys are kept in `trusted-senders.yaml` beside the person's tools. A file whose signature doesn't match is never opened. A signature never makes the contents trusted: everything is still reviewed and approved as before.
- **Policy:** `share_signers: [{name, key}]` lists keys the organization vouches for (shown as "your organization"); `require_signed_shares: true` opens only files signed by a key the person or the organization trusts (off by default). The audit line for each opening says who signed it.
- **Team library.** Tools › Team library: the person chooses a folder their team shares (a network drive, or a synced SharePoint, OneDrive or Dropbox folder). Columbus lists the `.columbus` files directly in it (at most 200; no subfolders or links), each with who shared it, who signed it, and how it stands against what is installed ("installed, the same", "different from yours (an update?)", "waiting for your review", "not installed"). Opening one works exactly as Open a shared file. Share saves into the library by default when there is one. The folder is kept in `sharing.json` beside the trusted senders.
- **Tools for everyone.** An administrator installs a shared tool for everyone on a computer with `columbus-mcp tools org-install FILE.columbus` (checked as any proposed tool is: exactly what Columbus builds from a proposal, its code within Columbus's rules; a changed signed file is refused). It goes to the organization's tools folder (`COLUMBUS_ORG_TOOLS`, or `tools` in ProgramData or /Library/Application Support/Columbus), approved: the administrator is the reviewer, and writing there needs one. Sessions offer these as "installed by your organization": confined like personal tools, no approval to run, and an organization tool wins over a personal tool with the same id (so workflows that use it run for everyone; `propose_tool` refuses that id). They are off until the policy says `allow_org_tools: true`; `deny_tools` can deny one. The folder must be the administrator's: on a Mac or Linux, the folder, `approved.yaml` and each tool's files must be owned by root and writable by no one else, and no part of it may be a link, or nothing in it loads; on Windows, make `ProgramData\\Columbus\\tools` writable only by administrators (as for the policy file). An organization tool that isn't ready hides nothing; with `require_signed_shares`, `org-install` takes only files signed by someone trusted, and every install is recorded before anything is written. `tools org-remove ID` and `tools org-list` manage them. The Tools page lists them, read only. Each install and removal is audited.

### Map snapshots

`map_snapshot` draws up to 8 of the session's own layers as a PNG that the assistant sees (and the app's chat shows the person, inside the step that made it): each layer its own colour, no web basemap, and nothing is downloaded to make it. Geometry only, unless the assistant asks for `labels` (`{"ws://…": "FIELD"}`): then that layer's features are labelled with that field's values, which the assistant can already read from the layer (plain text, cut to 40 characters, at most 400 labels, none overlapping; labels need Pillow in the engine). `snapshot_labels: false` in the policy keeps snapshots to geometry only. It can draw one of the session's own rasters underneath (`imagery`: aerial imagery, a DEM or a hillshade from a rasters connection), warped to the layers' CRS. It shows the assistant the shape of every feature in those layers, which the per-call row limit does not cap; an organization that treats geometry as sensitive can turn it off with `deny_tools: [map_snapshot]`.

**The person's view (`extent: "view"`, REQ-40).** With `extent: "view"` (and no `bbox`) the snapshot is of what the person's map shows now: the session's layers they have on (the 8 on top when there are more, the lowest drawn first; or the layers the assistant names with `layers`), at their map's extent. The extent comes from the map page's own report ([below](#the-assistant-and-the-map)); the engine draws the layers as the map does, in Web Mercator (EPSG:3857), cut exactly to that extent, so the picture has the shape of the part of the map the person sees. A view across the 180th meridian is drawn in one piece; latitudes stop at the edge of a web map's world (85.05°). The answer has `crs` (`EPSG:3857`) and `extent` in that CRS as always, and `view`: the same area as `extent` `[west, south, east, north]` in EPSG:4326, the `zoom`, how many of the session's layers are on the person's map (`layers_on_map`) and how many of them were left out of the picture (`layers_left_out`); each layer has `features` (the whole layer) and `in_view` (the features that reach the view). Everything else is as above: drawn by the engine from the session's layers alone, in the snapshot's own colours (not the map's), with no street background and nothing else the person has put on their map; `labels`, `imagery` (not across the 180th meridian), `snapshot_labels` and `deny_tools` work the same. With no map open it is refused in plain words ("the person's map is not open, so there is no view to draw…"), and so it is when the person has none of the session's layers on and none is named, or when the policy turns `map_view` off (the answer would say where the person is looking).

### The assistant and the map

The assistant can read what the person's map shows, and point it at a result (D-18, REQ-40). The person's map is the companion page ([below](#companion-window-and-desktop-app)): in the app's panel on the right, or in a window of its own.

- **The page says what it shows.** While it is on show, the page tells its session's server what its map shows. On show means: its window is visible (not a tab in the background), its map has a size, and, framed in the app, the panel on the right is open with this map in it (the app tells the framed page so, `shown` below; a page in a closed panel keeps its size in some web views, so it could not tell by itself). The report goes every second, and a quarter of a second after anything changes: the extent (west, south, east, north in EPSG:4326, of the part of the map no sheet covers; east passes 180 when the view crosses the 180th meridian), the zoom, the session's layers that are on (the list's top one first, at most 300), the active output, the selected feature (its layer's handle and its row, counted from 0), whether the table is open, and whether the street background is on. It is sent with the page's own session token (`POST /api/view`, from its own origin, as a decision is sent), which is checked before the body is read; a report is at most 96 KB. A page that is not on show says only that.
- **The server takes only that.** Every part is checked (numbers in range; a layer named only by a workspace handle of this session), and a report with any other key or value is refused whole (`400`), keeping what was there. The latest report of each open page is kept in memory, never on disk, and is not written to the audit log (one comes every second); a page not heard from for two minutes is forgotten. A map counts as open while a page on show reported within the last 5 seconds. With several windows of one session open, the person's map is the one they used last (a click, a key or the wheel in it; a window that has just come on show counts as used).
- **`map_view` with no arguments** returns `status: "open"` and the `view`: `crs` (`EPSG:4326`), `extent`, `zoom`, `layers_on` (handles, top first), `active`, `selected`, `table_open`, `street_background`, and how old the report is (`seen_seconds_ago`); or `status: "not_open"` with a sentence saying so. Only files the map lists are named (layers and tables in the session's results that a Columbus tool, an approved plugin or an approved script wrote). The selected feature comes as `{layer, feature, attributes, geometry}`: the page sends only the layer and the row, and the server reads that one row itself from the session's own layer, exactly as `read_output` would (attributes by field name; the geometry as its type and bounding box), so nothing a page sends is ever passed on as data. The attributes are left out when the policy denies `read_output` or returns no rows (`return_rows: 0`). The audit line of such a call records one row read, with the layer's data labels and provenance.
- **`map_view` with arguments** changes the view: `show` and `hide` (lists of handles of the session's layers, at most 50 each), `active` (a handle, layer or table: the output whose rows the table shows), `zoom_to` (a layer's handle, which also turns that layer on; or an extent `[west, south, east, north]` in EPSG:4326, west from -180 to 180, east greater than west by at most 360). Names that are not layers the map lists are refused before anything is asked of the map (a web layer's name or an address, another session's file, a file that is not a layer or table in the session's results, a table to draw, the same layer in `show` and `hide`). The change waits in the server; the person's map takes it with the answer to its next report (within a second), reads its list of results again so that a layer made a moment ago can be named, applies the change with the legend's own switches and the map's own zoom (a layer is fitted with the same padding as **Zoom to layer**; an extent with 24 px around it, no closer than zoom 19), shows "Your assistant changed what the map shows." for a few seconds, and reports the new view once the map shows it: the layers it turned on have been read, and its zoom has ended. The tool returns that view (`status: "changed"`, `asked`, `view`). It waits at most 8 seconds. A change no page on show took by then is dropped, and the answer is `status: "not_open"`, `changed: false` ("Nothing was changed…"), so it cannot move a map that opens later; only while a window of the session is being opened (the app asked for its panel's page, or a page signed in, within the last 15 seconds, and has not reported yet) does a change nothing has taken wait longer, 20 seconds in all, since a page needs a moment to load. A part the page could not do within 3 seconds (a layer it cannot draw, such as one whose file changed since Columbus wrote it; a zoom with nothing to zoom to) is named in `not_done`, with `status: "partly_changed"`, and a layer that is not drawn is not listed as on. A change the page took but did not confirm in time answers `status: "not_confirmed"`. One change is handed out at a time, to the person's map only.
- **No approval, and what that rests on.** `map_view` changes what is shown, never data, a source or a file, so it asks nothing; the person can move the map again at any time. Every call is an audit line (`map_view`, with whether it read or changed the view, or found no map); refusals too. `deny_tools: [map_view]` turns it off: the tool is refused and not offered by `search_tools`, the page's reports are not kept, and `map_snapshot` refuses `extent: "view"`.
- **In the app's own chat** a `map_view` call that changes the view opens the panel on the right if it is closed, even where the person closed it in this chat (they should see what the assistant shows them); a call that only reads leaves the panel as it is, and with the panel closed the assistant is told that no map is open. The step reads "Changing what your map shows" or "Looking at what your map shows".
- **Web map layers stay out of reach (D-14, REQ-34).** The page's report has no place for them: not their ids, titles, kinds, order, opacity, which one is the basemap, or whether any is on (`viewReport` in [`app/ui/src/view.ts`](../app/ui/src/view.ts), unit-tested for exactly its keys), and the server would refuse a report that carried any of it. `show`, `hide`, `active` and `zoom_to` take workspace handles and numbers only, so no web layer can be named. `street_background` is the street background's own switch; it reads `false` while a web layer is the basemap, and says no more.
- **Honest limits.** Moving the map moves what the map asks for: while the street background or a web layer is on, the page fetches tiles for the new area, as it does when the person moves it, so those services see an area the assistant chose. An organization that does not want that turns `map_view` off, or the street background (`companion: { basemap: false }`) and web layers (`map.allow_web_layers: false`). The view is as the page reports it: an extent, not pixels; the assistant does not see the street background, web layers or labels, and `map_snapshot` of the view draws the session's layers only. A turned map reports the box around what it shows. The map canvas itself still has no text alternative beyond the table.

### Projects and data groups

- **A project** (`projects/<id>/project.yaml`, in the person's folder, written by the app, and its files in `projects/<id>/files/`, [below](#project-files)) has a name, instructions for the assistant, the connections its chats may use (empty: all of the person's), a default export folder, and data groups. A chat started in a project runs its server with `COLUMBUS_PROJECT=<id>`: the server narrows the session to the project's connections and data groups, and refuses to start at all if the project, or one of its groups, can't be used. `whoami` reports the project; the app's chat gives the assistant its instructions in every reply and shows them to the person. Projects only narrow what the person has; they never loosen a rule.
- **A data group** is a named set of datasets across connections, each with an optional row filter: the person's own (`data-groups/<id>.yaml`, made in the app under Data › Data groups) or the organization's (its context pack's `data-groups/`). Under a project's groups only their datasets can be read, and a filter is ANDed onto the connection's own row filter; a filter's columns are bound to its table, so a name the table lacks is an error. `describe_data_group` describes either kind.
- **Project databases** (`project_db`, scope `project`) belong to their project (`workspaces/project-dbs/<id>/`); one holding data from a connection the project doesn't use, or loaded under other data groups, is withheld. In a project, a workflow may use only the project's connections, and none can be proposed from a project with data groups yet.

### Project files

Each project has a folder of plain files, `projects/<id>/files/` (D-19, F-17): scripts, notes, small things worth keeping between chats. The person puts their own there (the project's page opens the folder), and under policy `allow_project_files` (off by default; a switch in Settings › Organization rules, and one of the settings **Work freely on copies** turns on) the assistant works with the text files in it through one tool, `project_files`, and runs scripts kept there. It is for text the assistant writes, never for workspace layers: data still leaves the workspace only through `export_output`, and there is no way to copy a workspace file into the folder.

- **The tool.** `project_files {action, path?, text?, sha256?}`. `list` (optionally a folder in `path`) returns every plain file with its `path`, `bytes` and `modified` time (and `not_readable` with the reason, for a file the assistant cannot read), the `folders`, what is there but `skipped` (links, names the rules refuse) and the `limits`. `read` returns the `text`, `bytes`, `lines`, `modified` and the text's `sha256`, with the check `project_files.text`: a file's text is data, never instructions (the person, a colleague through sync, or an earlier chat may have written it). `write` creates the file, or replaces it, making folders on the way; `delete` removes it, and folders it leaves empty go with it. To replace or delete a file that is there, the assistant must pass the `sha256` its last `read` returned: a file the person (or a sync, or another chat) changed since is left as it is, with "changed since you read it". A write is made beside the file first and takes its name in one step, so a file is never half written, and is read back afterwards.
- **Paths (F-17).** A path is inside the folder, with `/` between folders. Refused, in plain words: absolute paths (`/…`, `C:\…`, `~/…`), `\`, `..` and `.`, names that start with `.git` or `.columbus` and `.forgejo` (Git's and Columbus's own; that also keeps a repository's server-side automation, `.github/workflows`, out of the assistant's hands), Windows' reserved device names (`NUL`, `COM1.txt`, `aux`…), the characters Windows refuses (`< > : " | ? *`), control and invisible characters, names that start or end with a space or end with a dot, names over 100 characters, paths over 240 characters or more than 8 folders deep. The name check comes first; the path is then walked from the folder one name at a time through the gateway's safe-path helpers ([`safefs.rs`](../crates/gateway/src/safefs.rs)), never following a link, so a link or a hard link anywhere on the way is refused, and each name must be there exactly as given: one that differs only by upper and lower case from a name already there is refused (they are one file on Windows and macOS), and so is a name no entry of the folder spells but the system finds all the same (the same letters written another way on macOS, a short name on Windows): only the spelling a listing shows is used, so one file has one name and one record of its labels. A files folder that is itself a link is not used.
- **Text only, and small.** UTF-8 text, at most 1 MB a file (larger files, files with a NUL byte and files that are not UTF-8 are not read, replaced or removed by the assistant). The folder may hold at most 1,000 files and 50 MB once the assistant has written to it (the person's own files count and are never removed). The listing stops at 1,000 files (`project_files.more`).
- **Not passwords, not programs.** Names that look like password, key or connection files are neither read nor written, whoever put them there (by name: `.env*`, `.netrc`, `.pgpass`, `id_rsa`, `*.pem`, `*.key`, `*.pfx`, `*.p12`, `*.jks`, `*.kdbx`, `*.ppk`, `*.sde`, `*.ags`, `*.odc`, `*.dsn`, `*.udl`): the assistant never gets a password or a connection file (B1). File types an operating system runs or follows when they are opened from the folder are never written by the assistant (`.bat`, `.cmd`, `.exe`, `.vbs`, `.js`, `.hta`, `.lnk`, `.url`, `.reg`, `.jar`, `.command`, `.desktop` and the like; `.py`, `.sql`, `.md`, `.json`, `.sh` and `.ps1` are fine); one the person put there can be read. `columbus-project.yaml` at the top of the folder (the project's shared settings, written when the project syncs) can be read, not written or removed.
- **Data labels follow the text.** What the assistant writes may quote data it has read. So a write is checked against the organization's `flows` rules as a flow from the session's data labels to `project:<id>` (a rule to `project:<id>`, `project:*` or `*` applies): a deny rule refuses it, a rule that asks for approval asks the person every time (the card shows the text), and with no rule it goes ahead. The file is recorded with the session's labels in `projects/<id>/files-labels.json`, beside the folder and never in it (so it does not sync), under a lock file; a session that later reads the file, or runs it, takes those labels on, exactly as if it had read the connection. A record that does not read stops every use of the files until the person removes it. Limits: a file the person or a sync changed or renamed keeps or loses its record by its path alone, and files that arrive by sync carry no labels.
- **Running a script from the folder.** `run_python` takes `script: "scripts/widths.py"` in place of `code`. The text is read as it is at that moment, through the same safe path and the same refusals, and everything else about the run is unchanged: the same script rules (plain text, lines of at most 200 characters, at most 100 KB), the same sandbox, the same approval rule (`scripts.approval`), and the code hash in the answer, the approval and provenance is the hash of the text that ran. So that a script can import helpers kept beside it, the other `.py` files directly in the script's own folder are copied beside it in the run folder, and that folder is first on Python's import path: at most 20 files and 1 MB in all, each within the script rules and with a name Python can import (letters, digits and `_`); subfolders are not copied. Files that are not taken are named in the check `script.helper_skipped` (warn). Where a run is approved, the card names the file and its helpers ("from the project's file scripts/widths.py, with 1 helper file from its folder (geom.py)"), the approval is bound to each helper's SHA-256 as well as the script's, and a session approval covers the script only while its helpers are unchanged. Provenance records the script's `project`, `path` and `helpers` (name, hash, lines) beside its code.
- **No project, or the policy off.** In a chat that is not in a project, every action (and `run_python` with `script`) answers that project files need a project: "…Ask the person to start the chat in a project…". While `allow_project_files` is off, the tool is not offered (`search_tools` leaves it out, `describe_tool` and every call refuse it, naming the switch), and `whoami` says `policy.project_files_allowed: false`.
- **Audit.** Every action is one audit line (`tool: project_files`): `dataset` is `project:<id>/<path>`, `reason` says what happened (`created, N bytes, sha256 …`, `replaced with …`, `read …`, `deleted …`, or why it was refused), with the data labels and the flow decision of a write. The text itself is never in the log (the request is recorded by the text's hash). A script run from the folder has the same `dataset` on its `run_python` lines.
- **In the app.** A project's page has a **Files** section: each file's name, size and when it changed, under its folder, with **Open the folder** (the folder is made if it is not there, and shown in Explorer, Finder or the desktop's file manager) and **Check again**; it says when project files are turned off for the assistant, and lists what is there but not offered (links, refused names). The app lists names only, never following a link, and opens no file. Deleting a project removes its settings; its files stay in its folder.
- **Tests.** [`tests/project_files.rs`](../crates/gateway/tests/project_files.rs): a chat in a project writes a script and a helper, lists, reads, runs the script by its path, changes and removes it, each step audited; every refused path and file kind above (with nothing outside the folder read or written, and nothing in it changed); a chat with no project, and the policy off; labels kept across chats and the two kinds of flow rule; the approval card naming the file and its helpers. The desktop script [`projects.py`](../app/desktop/e2e/projects.py) opens the folder and checks that a file a real session wrote is listed with its size and time.

## Toolboxes

A **toolbox** is a command-line program that describes its own tools (build brief 3, D-17). The person installs one; Columbus reads its description and offers every tool to the assistant through the three tools it already has: `search_tools` finds one, `describe_tool` shows its parameters, and `run_tool` runs it as `<toolbox>.<tool>` (`geolibre.slope`). Nobody writes a wrapper per tool: Columbus keeps one adapter per *kind* of program. A toolbox's program is somebody else's code, so it never runs outside the sandbox, and only while its file is the one that was installed.

**The format (F-16).** `toolboxes/<id>/toolbox.yaml`, in the person's toolboxes folder (`toolboxes` beside their tools folder; `COLUMBUS_TOOLBOXES` overrides). Columbus writes it; unknown keys are refused. [`examples/toolboxes/linetools`](../examples/toolboxes/linetools) shows one.

| Key | What it holds |
| --- | --- |
| `id` | The folder's name and the prefix of its tools: lowercase letters, digits and `-`, starting with a letter, at most 40. Ids of other providers and `columbus`, `personal`, `rustgis`, `gdal`, `pdal`, `whitebox`, `duckdb` are refused |
| `name` | A name for people |
| `kind` | `geolibre` or `described` (below). `qgis` is named by F-16 but not built: it is refused with a plain message |
| `program` | The program's absolute path |
| `sha256` | SHA-256 of the program file. Checked before every run, and before Columbus runs the program to list its tools. A changed or missing program is not run, and its tools are no longer offered, until the person installs it again |
| `version`, `source`, `licence`, `installed` | Its version, where it came from (the download address, or the file the person chose), its licence as stated, and when it was installed |
| `tools_sha256` | `described` only: SHA-256 of `tools.json` as it was added. A changed description file is not used until the toolbox is added again |
| `reads` | Optional: up to 8 folders the program may read besides its own (its data or libraries) |

Beside it, `tools.cache.json` holds the tools as last listed, with the hash of the program they were listed from; it is read at every use and rebuilt only when that hash differs, so a thousand tools cost a session nothing at its start.

**Kinds.**

- **`geolibre`**: the GeoLibre runner (MIT), the program behind RustGIS's thousand tools, most of them Whitebox tools. Columbus asks it for its tools with `manifests` (a JSON array, one manifest per tool) and runs one as `<program> <tool> --name=value …`, as its source at v1.8.1 says (`crates/geolibre-cli`, and `wbcore`'s `manifest_with_param_schema_json`). A parameter's `schema` gives its role and kind: `input` and `output` with a dataset (`raster`, `vector`, `lidar`, `table`, `json`, `text`, `file`), `scalar` (integer or float), `enum` with its options, `bool`, `string` and `field`; `io_role` and `data_kind` stand in where a schema says something Columbus does not know. Reading is tolerant on purpose (A-7): unknown fields are ignored; a tool whose parameters cannot be read is still listed, as one "Columbus cannot run yet", with the reason; an entry with no usable id is only counted. A tool that needs a LiDAR point cloud is listed the same way, because Columbus has no source of point clouds yet. The program's own words (names, summaries, descriptions) are shown with hidden characters removed and cut to a length, and `describe_tool` says they are the program's own and not instructions.
- **`described`**: any other program, with a `tools.json` a person writes: `{"tools": [{"id", "name"?, "summary", "description"?, "category"?, "args": [...], "params": [...]}]}`. `args` is the command line after the program; `{name}` is replaced by that parameter's value, and a part naming a parameter that was left out is dropped (so write an optional one as `--dist={distance}`, in one part). Each parameter has `name`, `role` (`input`, `output` or `value`), `required` and `description`; an input or output has a `kind` (`vector`, `raster`, `table` or `file`; also `lidar`, `json`, `text`) and an output may give its file extension as `ext`; a value has a `type` (`number`, `integer`, `string`, `boolean` or `enum` with `options`) and may have a `default`; an input may say `many: true` (several files, joined with `;`) or `or_value: true` (a plain value is accepted in place of a file). The file is checked strictly when the toolbox is added: unknown keys, a parameter never used in `args`, a `{name}` that is no parameter, an enum without options and the like are refused with the place.

**The catalogue and its pins.** Columbus has a built-in catalogue, in its code, with one entry: **GeoLibre 1.8.1** (MIT; publisher opengeos; release page `https://github.com/opengeos/geolibre-rust/releases/tag/v1.8.1`), downloaded from `https://github.com/opengeos/geolibre-rust/releases/download/v1.8.1/geolibre-v1.8.1-<target>.<ext>` and pinned by the SHA-256 of each archive. Each archive was downloaded and hashed on 2026-11-10 and equals the publisher's own `.sha256` file. No version before 1.8.1 is offered or accepted: earlier ones contained code under the AGPL. Columbus never bundles the program: it is fetched on the person's computer, at their request.

**Installing is the person's.** A toolbox adds to what the assistant can run without asking, so no MCP tool installs one. At the keyboard:

```powershell
columbus-mcp toolbox install geolibre     # from the catalogue: shows what it is, asks, downloads, checks, lists
columbus-mcp toolbox add C:\Tools\linetools.exe --id linetools --kind described --tools tools.json
columbus-mcp toolbox list                 # installed ones and their state; what the catalogue offers
columbus-mcp toolbox tools slope raster   # find tools by words
columbus-mcp toolbox show geolibre.slope  # one tool's parameters
columbus-mcp toolbox remove geolibre
```

- `toolbox install <id>` refuses at once unless policy allows it (`allow_toolboxes`, and `toolboxes.catalogue` for the download), shows the name, version, publisher, licence, download address, size and pinned hash, and asks the person to type the id on the terminal itself (`--yes` answers for a script, as the app does after its own confirmation; `--json` prints one line per step). It downloads over HTTPS only (redirects followed only to HTTPS; at most the stated size; time limits), and checks the archive's size and SHA-256 against the pin **before** unpacking. It then takes out only the files it expects (the program, and the publisher's `LICENSE` and `THIRD-PARTY-NOTICES.txt` beside it), to names of its own choosing: no path from the archive is used, and an archive that holds an absolute path, a `..`, a link or a device is refused whole. On macOS and Linux the program is made executable. It records the program's own SHA-256 in `toolbox.yaml`, runs the program in the sandbox to ask for its tools, and only then moves the toolbox into place. Anything that fails or is refused leaves nothing behind. Installing again replaces a catalogue install of the same id (this is how a changed program is put right); a toolbox the person added under that id is never replaced.
- `toolbox add <program> --id <id> --kind geolibre|described [--tools tools.json] [--name …] [--version …] [--licence …] [--reads <folder>]…` adds a program already on the computer: a `described` one, or a GeoLibre runner installed by hand (asked for its `version` in the sandbox, and refused if it says it is older than 1.8.1). It shows the program, its hash and exactly which folders its tools will be able to read (the program's own folder and any `--reads`), and asks for the id typed on the terminal. The program stays where it is; put it in a folder of its own, because its tools can read that whole folder.
- `toolbox remove <id>` deletes the toolbox's folder (with the program, when the catalogue put it there; a program the person added stays where it is). Running sessions stop offering its tools from their next call.
- Each install, add and removal, refused ones included, is a line in the audit log (`toolbox_install`, `toolbox_add`, `toolbox_remove`; client `columbus-mcp toolbox`).

**In the app.** The Columbus app's **Tools** page opens with a **Toolboxes** section (build brief 3, T-29; `app/desktop/ui/js/pages/toolboxes.js`, commands in `app/desktop/src-tauri/src/toolboxes.rs`):

- *Installed.* Each toolbox with its name, version, how many tools it lists (and how many of them Columbus cannot run yet), where it came from, its licence and when it was installed. One whose program changed, is missing or cannot be read says so, with what to do. **Remove** takes it away (through `columbus-mcp toolbox remove`, so it is in the audit log); nothing is confirmed, because removing only takes away.
- *Add tools.* A dialog with what Columbus's catalogue offers on this system (for GeoLibre: one line on what it is, then its version, the size of the download, its licence, its publisher and the address it is downloaded from) and **A program on this computer** (the program's file, its `tools.json`, a short name and a name: a `described` toolbox). Nothing is downloaded until the person presses **Install**. Installing and adding are confirmed at the keyboard in the app's own code, as installing a personal tool is: Touch ID or the account password on macOS, Windows Hello on Windows. Only then does the app start Columbus's own server to do the work (`columbus-mcp toolbox install <id> --yes --json`, or `toolbox add … --yes --json`), so the app and the terminal install in exactly the same way; the dialog shows each step (the download with its progress, the check against the pin, the unpacking, the listing in the sandbox) and then how many tools are ready. Where the app cannot confirm who is at the keyboard (Linux), the dialog shows the terminal's command instead of a button. A system the publisher builds nothing for (Windows on ARM), and a policy that stops downloads (`toolboxes.catalogue: false`), are said plainly, with no Install button.
- *Finding a tool.* A search box lists the tools of the installed toolboxes by the words typed (the same ranking the assistant's `search_tools` uses; the first 40, and how many matched): each with its name, the name the assistant calls it by, its one-line summary, its toolbox and its category. A tool Columbus cannot run yet is marked. A row (click, or Enter on the keyboard) opens the tool in the panel on the right: what it does and each parameter with its role, its kind or type, whether it is required, and its default.
- *Turned off.* With `allow_toolboxes` off, the section says toolboxes are turned off and how to turn them on (the **Work freely on copies** choice in Settings, or the organization's policy file), and offers nothing: no Add tools, no search. Installed toolboxes stay listed, as off, and can still be removed.

The page only reads the files beside each toolbox, so it shows what the assistant is offered; it never runs a toolbox's program itself (the server does, in the sandbox, when it installs or adds one). The app's seven toolbox commands are open to its main window only, like its other commands.

**Finding and describing.** `whoami` (`policy.toolboxes_allowed`, a provider card per toolbox, and a note) and `list_providers` (kind `toolbox`, level `A`, how many tools) tell the assistant the toolboxes are there. `search_tools` matches the query's words against each tool's id, name, summary and category (and the toolbox's name), ranks them (a word that is the id counts most), and adds at most 20 toolbox tools to its answer; when more matched, the check `search.more_in_toolboxes` says how many, and `provider: "<toolbox>"` searches one toolbox alone. Among tools that matched as many words, Columbus's own tools and the person's come first. `describe_tool` gives the tool's summary and category, each parameter with its role, its kind or type, whether it is required, its choices and default, and one paragraph on how to run it; its `input_schema` is a JSON Schema of the arguments and `reviewed_hash` is the program's hash.

**A run.** Under `allow_toolboxes`, with no approval (D-16: installing was the person's decision, and the sandbox is the boundary):

- *Arguments.* Each input is a workspace handle (`ws://…`) of a file a Columbus tool, an approved plugin, a script or a toolbox tool wrote in this session, unchanged since (never a connected server's file); a list of handles where the parameter takes several. Outputs are left out: Columbus names each one `<parameter>.<extension>` in the run's `out/` folder (`.gpkg` for a vector layer, `.tif` for a raster, `.csv` for a table, `.json`, `.txt`, or the `ext` a description gives). The assistant may set an output to a plain file name to choose its name, to `false` to leave it out, or to `true` to ask for an optional extra one: by default a tool's main outputs are written (a required one, one named `output`, the only one, or all of them when there is no main one). Values are checked against their type. For a `described` tool everything is held exactly (an unknown argument or a choice not among the options is refused). A GeoLibre tool's description is partly the program's own guess from its help text, so there Columbus is forgiving and says so in a check: an argument the tool does not list (`toolbox.unlisted_parameter`), a choice not among those listed (`toolbox.unlisted_choice`) or a plain value for a parameter described as a file (`toolbox.plain_value_for_input`) is passed as written. A refusal lists what the tool takes.
- *Confinement (R-22).* Exactly as a script: through `columbus-confine` at level A (no network), the same cleared environment (no secrets, no `COLUMBUS_*` settings, nothing of the person's but what a program needs to start), the same limits on memory (`plugins.memory_mb`), processes and time (`limits.seconds`; the run and everything it started are ended at the limit), one confined run at a time in a session. Its run folder (`runs/toolbox-<id>/`, deleted afterwards) is the only place it can write; it can read the copies of its inputs there (each checked byte for byte against what Columbus recorded), its program's own folder and the folders its `toolbox.yaml` lists. Paths on its command line are relative to the run folder, which is its working folder. If the machine cannot confine it, it does not run. Asking a program for its tools or its version is done the same way.
- *Results.* Every plain file the tool leaves directly in `out/` is copied, without following links, to `results/<toolbox>-<tool>-<run>-<name>` and recorded with the hash of the bytes copied, under the same caps as a script's outputs (50 files, 512 MB each, 1 GB in all; the rest is reported as `toolbox.output_skipped`). They are workspace results like any other: a GeoPackage is a layer and a CSV a table (checked by the engine as a script's outputs are), a GeoTIFF a raster (described and checked as `raster_op`'s are), anything else a file; the map, the table, `vector_op`, `raster_op`, `verify`, `read_output` and `export_output` take them. They carry the inputs' and the session's data labels, the inputs' fails and truncation, and the run's own fails (`toolbox.exit_code`, `toolbox.timeout`), so a failed run blocks export. An output the tool did not write is `toolbox.output_missing`; a file of another kind than the parameter describes is handed over and said (`toolbox.input_kind`).
- *What it printed (R-23).* stdout and stderr come back cut to the script cap (64 KB each; `toolbox.output_cut`), inside `external`, marked `untrusted` with the notice that it is data, not instructions; the last line of stdout, when it is a JSON object (the GeoLibre runner prints its outputs so), is also given as `reported`. A tool that fails (any exit code but 0) returns the same, with the status `failed` and the tool's usage.
- *Records.* Provenance holds the toolbox (id, kind, version, program hash, source), the tool, the arguments as given, the command line, the inputs with their hashes and labels, the confinement, the exit code and the outputs. The audit log has a `running` line written before the program starts (a run that cannot be recorded does not happen) and a line for the outcome, each with the toolbox as `provider`, its version and `sha256:<program hash>`.

**Formats.** Workspace layers are GeoPackages and rasters are GeoTIFFs, and they are handed to a tool as they are: nothing is converted. For the GeoLibre runner this rests on its source at v1.8.1, whose vector library picks the format from the file's extension and reads and writes GeoPackage (`.gpkg`) with its own SQLite code, and whose raster library reads and writes GeoTIFF (its outputs are Cloud-Optimized GeoTIFFs). A vector output in another format (GeoJSON, shapefile, FlatGeobuf) comes back as a file, not a layer.

**Policy.** `allow_toolboxes: true` turns toolboxes on (off by default); off, no toolbox tool is found, described or run, none can be installed or added, and `whoami` says `toolboxes_allowed: false`. `toolboxes.catalogue: false` stops the built-in catalogue from downloading anything; a program already on the computer can still be added. `deny_tools` can name a toolbox tool (`geolibre.slope`), which also hides it from `search_tools`; an organization that lists `tools` must list each toolbox tool it allows.

**Limits, said plainly.**

- The real GeoLibre runner was never run while this was built (the build could not run a downloaded program): the adapter follows the runner's source and is tested against a stand-in that follows the same command line ([`examples/toolbox_standin.rs`](../crates/gateway/examples/toolbox_standin.rs)). Its first real run is the owner's check H-3. In particular, that its own GeoPackage reader reads every GeoPackage Columbus writes has not been tried.
- The hash shows the program is the file its publisher released (or the one the person added). It says nothing about whether the program's results are right: check them as you would any analysis. Inside the sandbox the program can still read its inputs and waste time or write nonsense; it cannot reach the network, a connection, a password or the person's other files.
- The GeoLibre runner works out the type of each value on its command line itself (`true`, `12`, `2.5`, else text), so a text value that looks like a number reaches a tool as a number. Its tools that fetch from the network do not work in the sandbox.
- Workflows cannot use toolbox tools yet: a step is still a reading or checking tool or a personal tool. QGIS is not a kind yet. Point clouds have no source in Columbus.

## Connected MCP servers

Columbus is an MCP client to other servers too (design change 1, "governed MCP host"). Each one needs a **Columbus manifest**, written or approved by a person or IT, under `%ProgramData%\Columbus\servers\` (personal manifests under `%APPDATA%` only if policy allows). The manifest decides everything: which tools are on, their risk, whether they send data out, which arguments are files, paths or URLs, and when to ask. The server's own hints are shown at review and never trusted. See [`examples/servers`](../examples/servers).

| Rule | What Columbus does |
| --- | --- |
| 1. New and changed tools start off | Every tool definition is hashed at approval. On each connect the gateway re-hashes; a changed description or schema, or a new tool, is switched off until a person reviews it |
| 2. Data moves as files | File arguments take workspace handles only; the gateway sends the file's bytes. Results marked `to_workspace` are saved as files and a handle comes back |
| 3. Data-flow approvals | Reading a governed connection labels the session (`connection:roads-prod`) and its files. While a label is active, any write or upload to a connected server needs the person's approval, whatever its manifest says; organization `flows` rules can forbid it outright |
| 4. External output is untrusted | Connected servers' results are wrapped as data, never instructions |
| 5. Local servers run confined | Local (stdio) servers and engine plugins start through the `columbus-confine` launcher at the level their manifest declares (A when none), capped by policy (below). They also get a scrubbed environment and a folder of their own in the workspace (`servers/<id>`, `plugins/<id>`), the only place they can write; they never see the workspace's results or governed extracts. A file handed to a server or plugin is copied into its folder once the call is allowed, and a plugin's outputs are copied out into `results/` by Columbus, with the hash of exactly what was copied. Remote servers must be on the policy's host list |

Review is done by the person at the keyboard:

```powershell
columbus-mcp servers list                 # each server and its state (trial, ready, needs review, blocked)
columbus-mcp servers review drive         # tools, the manifest's settings, the server's claims, and flags
columbus-mcp servers approve drive        # pins the definitions; asks you to type the id on the terminal
```

Remote servers that use OAuth (`auth: { type: oauth, scopes: [...] }`) are signed in to by the person, once, in their own browser:

```powershell
columbus-mcp servers signin drive         # opens the sign-in page; the redirect comes back to 127.0.0.1
columbus-mcp servers signout drive        # forgets the tokens
```

Sign-in follows the MCP authorization specification (OAuth 2.1 with PKCE; a client id from the manifest, or dynamic client registration as a native application). The tokens are kept in Windows Credential Manager, one entry per server, and added and refreshed by the gateway; they never reach the agent, tool results or the audit log, and no server receives another's. Scopes are the manifest's, never wider: a grant with any other scope is discarded and the sign-in fails. Until a server is signed in, `list_providers` shows it as `sign_in_required` with the command to run.

Review flags descriptions with hidden characters, wording aimed at the model ("ignore previous", "do not tell the user"), references to other providers' or Columbus's tools, credentials and destinations. Flagged tools need `--accept-flags`.

When a call needs approval, Columbus asks the person in their own MCP client (elicitation); the agent never sees or answers that prompt. When the client cannot ask, Columbus opens its **local approvals page** in the person's browser and the call waits briefly (45 s by default) for the decision. If none comes in time, the agent gets `approval_required` with an id, tells the person, and calls again with that id once they have decided. `whoami` tells the agent which way approvals will reach the person.

The approvals page is served only on 127.0.0.1 on a random port and uses no cookies (browsers share 127.0.0.1 cookies across ports, so another local program could collect them). The browser is opened on a single-use link whose secret sits after `#`, which browsers never send to any server; the page trades it once for a session token it keeps only in memory and sends in a header other websites cannot set. Requests for any other host name are refused, and decisions must come from the page's own origin. The page shows what would happen in plain words (destination, files and row counts, which connections the data came from, the flow rule that applied, the arguments) and the exact request on demand. Every decision is written to the audit log, and the agent never receives the page's address.

An approval is bound to exactly what will be sent: each file's SHA-256 and size and the data labels in play, not just the file's name. A file changed after approval, including under "allow for this session", is asked about again; a file a tool reads itself is checked again just before the call. Identical waiting requests share one approval, at most 20 may wait at once, and Columbus stops opening tabs after 10 without a decision. Organization policy can turn the page off or change the wait (`approvals: { page, wait_seconds }`).

Known limits: an agent that can run programs as the person could read the browser's command line in the instant it starts (the link is single-use, so the person would then see "already used"), and an agent that controls the person's browser can press its buttons. Give such agents only connections whose database logins are read-only.

### Confinement levels

| Level | On Windows | On macOS | Files | Network | For |
| --- | --- | --- | --- | --- | --- |
| A | AppContainer, no capabilities | Seatbelt profile, no network | its own folder in the workspace and declared folders only | none | scripts, personal tools, toolbox tools, engine plugins (the default) and compute-only servers |
| B | AppContainer with internetClient | Seatbelt profile, IPv4 internet only | same as A | internet, not loopback | local servers that call public APIs themselves |
| C | not available yet (see below) | Seatbelt profile | reads what the person can; writes only its own folder and declared folders | loopback and anything else | servers that drive a desktop app (Obsidian, QGIS, ArcGIS Pro add-ins); needs `trust: trusted` or an allow-list entry |

On Windows every level also runs in a job object (on macOS, see below): the process and anything it starts end when the gateway stops it, with memory and process limits (`servers.memory_mb`, `plugins.memory_mb`). The program's own folder and, for Python plugins, the interpreter's folders are readable; nothing else in the person's profile is. Policy lists the levels allowed: `servers.levels` (default A, B, C) and `plugins.levels` (default A; plugins never get C). `list_providers` shows each provider's level.

Confinement fails closed. If a level cannot be provided (the launcher is missing, or the operating system has no implementation), the server or plugin is blocked, unless `servers.allow_unconfined_local` allows an unconfined pilot, which `list_providers` then shows as `unconfined`. On Linux, used for development and CI, the launcher uses Landlock for files and a seccomp filter for system calls ([`crates/confine/src/linux.rs`](../crates/confine/src/linux.rs)). *Files at A and B:* the system's program folders (`/usr`, `/lib`, `/bin`, `/sbin`, `/opt`), the processor list, and of `/etc` only a short list of names: what the loader, the C library, the certificate stores and language runtimes need to start (`ld.so.*`, `localtime`, `passwd` and `group` for user names, `ssl`, `pki`, the `python*`, `java*` and `R` folders Debian links there, and a few shared tables). The rest of `/etc` is closed, so the organization's own folder there (`/etc/columbus`: the policy file, the audit log, server settings) and other programs' settings, which can hold database logins (`odbc.ini`, `pg_service.conf`, `fstab`), cannot be read; level B adds the resolver's files (`resolv.conf`, `hosts`). Nothing in `/proc` can be opened: a confined program cannot list processes or read their command lines, and Landlock itself refuses it the memory, environment and open files of every process outside its sandbox (the gateway also marks itself non-dumpable). `/dev/tty` is closed at A and B (where the gateway was started from a terminal, a program could otherwise read what the person types there). Files the launcher was handed besides its input and output are closed before the program starts. *Network:* level A makes no socket of any kind, only stream socket pairs (so no internet, Unix, netlink, virtual-machine or Bluetooth sockets); level B only IPv4 and IPv6 ones; a datagram socket pair is refused at both, because one can be pointed at any Unix datagram socket outside the sandbox; io_uring is refused at every level. *Other processes:* A and B cannot leave the process group (so stopping a program stops everything it started), use the kernel's key store, System V shared memory or message queues of either kind, and, where the kernel has Landlock's scopes (6.12 or later), cannot signal a process outside the sandbox. *Permissions and times:* Landlock has no say over changing a file's permissions, owner, times or extended attributes (`chmod`, `chown`, `utime`, `setxattr`), so at A and B these calls do nothing and report success: no file's permissions or times change, outside the sandbox or in it, and `shutil.copy` and `copy2`, which make the same calls on the copy, go on working (a new file still gets the permissions it is created with; a script that needs a program of its own making runs it through its interpreter). *The filter itself:* a call made by its 32-bit number ends the program, and on x86-64 one made by its x32 number is refused, so no rule can be stepped around by another numbering. Run as root, the launcher drops every capability first. The gateway reaches into a confined process's folder only by walking it from the workspace root without following links, so a link planted there is refused, never followed. Known limits on Linux: the process count is not capped (memory is, per process); level C, which reads everything, can still change the permissions and times of files the person owns (never the contents or the name); before kernel 6.12 it can signal the person's other processes, and before 6.2 `truncate` is refused outright (it could otherwise empty a file); a confined program cannot use `multiprocessing` locks and pools (they need `/dev/shm`), though threads and subprocesses work. On Windows level C (planned as a restricted token at low integrity) is refused for now: on the systems tested, a low-integrity process could not read ordinary program folders, so it would not do what the level promises; a server that needs it is blocked until it is fixed, or can run at A or B with the folders it needs. On macOS the launcher runs the program under the system sandbox (Seatbelt, through `sandbox-exec`) with a profile it writes for each launch, every path passed as a parameter, never spliced into the rules. At every level the program is refused the system services that would act for it outside the sandbox (opening apps, Apple Events, the pasteboard, the keychain); at A it is also refused the certificate service, which fetches from the network for its caller. It cannot list other processes. macOS has no job object, so the launcher tags each launch's sandbox and finds every process in it, even one that left the process group; it sums their memory and counts them many times a second, and stops them all, round after round until none is left, past a limit, when the program ends, when the gateway goes, and (through a guard process) if the launcher itself is killed. A per-user process limit set on the program is a kernel backstop against a fork burst between two looks. Before the first launch it checks that this works and refuses confinement if not. Known limits on macOS: Apple marks `sandbox-exec` as deprecated, so a future macOS may change it (the check above then fails closed); Apple's base rules let a confined program reach a few services (preferences, logging, notifications, user names); level B opens IPv4 connections only, because the sandbox's network rules can name `localhost` but not an address and an IPv6 address can name this computer past them, so B does not work on IPv6-only networks; it cannot reach `localhost` but can reach this computer's own network address and other machines on the local network; level C refuses a list of services known to act outside the sandbox, so a service not on that list may still answer it; programs confined at the same time can pass data to each other through shared system state (notifications, named semaphores), so a script at A could hand data to a server running at B or C; any confined program may learn whether a file exists and its size and dates, though not its contents; a confined program can read the arguments and environment that other programs of the same user were started with, which the sandbox does not cover, so while a local server that gets an API key in its environment is running, an engine plugin or script could read that key (Columbus's own passwords never go in an environment); the memory limit is checked many times a second, not enforced by the kernel. Passwords are kept in the macOS Keychain.

Columbus's own engine worker is not confined: it is Columbus's code, it reads the connections (files, databases on the network or on this machine), and it is what enforces the rules on the data.

Not yet: the RustGIS worker (milestone 2 of change 1), and Windows' own MCP containment as an extra level once it leaves preview.

## Context pack

An organization describes its GIS world in a **context pack**: a folder of Markdown and YAML (datasets with their gotchas, coded domains, linear referencing, data groups, delivery specs, SOPs, roles), installed under `%ProgramData%\Columbus\context` (or `COLUMBUS_CONTEXT`). Agents search it with `context_search` and read entries with `context_get`; `describe_dataset` attaches the matching dataset entry, `describe_data_group` resolves a group's datasets and says which this session can read, and `whoami` returns the pack's always-on rules. Entries past the pack's review interval come back marked `stale`. `columbus-mcp pack lint DIR` checks a pack. See the [format](context-pack.md) and the fictional [Contoso County](../examples/context/contoso-county) sample.

**The person's own notes.** `draft_notes` (or **Draft notes** on a connection's page in the app) writes notes about a connection's datasets into the person's notes folder (`notes/` beside the session workspaces, or `COLUMBUS_NOTES`), in the context pack format: what the database says about itself only, never what it means (principle 10). Each dataset gets its fields and types, geometry and CRS, the row count within the connection's row filter, primary key, relationships, indexes and the comments written in the database (PostgreSQL `COMMENT`, Oracle `COMMENT ON`, SQL Server `MS_Description`, GeoPackage data columns); each short code field (up to 30 distinct values, ids and long text skipped, tables up to 2 million rows) gets a code list with how many rows have each code, labelled where the GeoPackage gives labels. Codes are counted by checked SQL, so the row filter applies; organization policy can turn code lists off (`notes: {values: false}`). Fields the organization hides, and tables the connection refuses, are never written, a relationship to a refused table is kept without its name, and nothing is written to the database. Every note is `status: draft`; a later draft never replaces a note anyone edited (each draft carries a hash of itself) or marked reviewed. The AI fills in meaning with `update_notes` (titles, summaries, field aliases and notes, code labels, text), on drafts only: a whole batch of changes, to up to 200 notes, is shown and approved at once, all or nothing, and the person may choose **Allow for this session** (**Allow for this chat** in the app's chat), which covers later changes to the person's draft notes in that session, and each flow of data the card showed (data a session read, put into notes about another connection, is named on the card; a change that would put data anywhere not yet shown asks again; an organization rule that asks for approval, or `notes.ask_each_change`, asks every time and does not offer it). What "allow for this session" covers is fixed when the person is asked and said in the prompt, on the approvals page and in the app. Organization policy can require approval of every change (`notes: {ask_each_change: true}`). The context tools and `describe_dataset` read the notes beside the organization's pack (whose entry wins on the same id), as the rules in force now allow: a note about a connection that is gone, a dataset no longer allowed or a field now hidden is not shown, or shows without that field. They are labelled as the person's own and as information, not instructions; nothing in them becomes an always-on rule. Serving a note about a connection labels the session with that connection, exactly as reading it would, so the organization's flow rules apply to what the notes say. Each note records the rules it was drafted under (the dataset's filters, the hidden fields, whether codes were listed): when those differ, its code lists and counts are not shown until it is drafted again. Codes are listed only where the assistant could read rows anyway (a row tool allowed and `return_rows` above 0), and no more of them than a call may return. Names from the database that hold control or line-break characters are left out, and every note is read back after it is written: one that does not read back as the note it should be (its id, kind, connection and dataset) is removed. `update_notes` is bound to the note file's exact contents, refuses if it changed while the person decided, and changes the file as it is, so nothing the rules hide today is lost from it. Organization policy can deny `draft_notes`, for the app's button too. What `update_notes` writes is checked against the organization's flow rules as a write into that connection (data this session read from elsewhere, written into notes about it), and the note records the data labels it then carries (`carries`), which every later reader of the note takes on; only notes about a connection can be updated. A note's counts are never in its summary, and a note drafted before the rules changed says so (`redraft`). Ids join their parts with `--` (a slug never holds two dashes), and a draft never takes a file or id another dataset's note has.

**What in the notes needs the person.** The app's Documentation › Proposals checks the notes (`columbus-mcp notes check '{}'`, read only): each note about a dataset against the fields its connection lists now, through an in-process Columbus session under the rules in force (each listing audited as client `columbus-app-page`), showing fields added, gone or now hidden, or of another type, and datasets no longer there or allowed; and every note the context tools would call stale (its `last_confirmed` older than the notes' `review_interval_months`). Retired notes, and notes that name no fields, are left out; field names are matched exactly (or, failing that, by the one name that differs only in case); field names with characters a person can't see are never offered; at most 50 connections are checked at once; linked folders in the notes are not followed. A changed draft no one has edited can be drafted again from there; an edited or reviewed one is the person's to update (the app offers to ask their assistant to look, with a short message of visible text only, which the person sends themselves). **Read and confirm** shows a reviewed note's text and, on **Yes, it's still right**, sets its `last_confirmed` to today, changing only that value and only if the file is still exactly the text shown; a draft is reviewed under My notes instead. **From your assistant:** an assistant can suggest note changes instead of asking now (`suggest_note_changes`: the same changes as `update_notes`, plus a one-line `why`). A suggestion is checked as `update_notes` checks (plain text; the note's own fields and codes; the flow rules for what the session has read), can be for a reviewed note (which the assistant can't change itself), and is kept under `proposals/` in the notes folder, which no context tool reads (at most 200 waiting). The app lists them with what each changes, why, which assistant and when, and whether the note changed since; **Accept** makes the change as the person (`columbus-mcp notes suggestions '{"accept": ID}'`), checked again against the note as it is now and the rules in force now, all or nothing, and the note then carries the data the suggesting session had read; **Dismiss** drops it. What accepting writes is exactly what the list showed (the app sends back the hash of it), and what a suggestion says is checked against its audit record (the record holds the hash of the suggestion and the data the session had read), so a suggestion changed on disk afterwards can't be accepted. Suggesting, accepting and dismissing are each audited; the accept record names the suggestion, its hash, who suggested it and the notes' files before. `deny_tools: [update_notes]` turns suggestions off too.

**Importing documents into the notes.** In the app (Documentation › Import), the person chooses a Word (`.docx`), Excel (`.xlsx`), PDF, CSV, Markdown or text file; Columbus shows what it becomes, and the person adds it as an SOP (with when to use it), a reference note or a glossary, with a title and a one- or two-sentence summary. It is written to the notes folder as `imported/<id>.md`, `status: draft`, with a line saying where it came from, and the original is kept beside it under `sources/imported/<id>/`. Only text comes in (headings, paragraphs, numbered and bulleted lists, tables; long tables and texts are cut, and say so): no macros, links, images or embedded objects are run or followed; Word and Excel parts that aren't UTF-8 or that declare a document type or entities are refused, every part is capped in size, and work stops once the text reaches its cap. Text hidden in Word and hidden sheets in Excel are left out, with a warning, and characters a person can't see (controls, zero-width and direction marks, Unicode tag characters, variation selectors) are removed, so the preview shows all there is. The document is read confined when the computer can (as scripts are: no network, writing only its own folder, at most 1.5 GB of memory) and in the engine otherwise, within 120 seconds either way; which is decided before anything reads the document, a confined read that fails is never tried again unconfined, and an unconfined read says so in the preview and the audit. The reader's answer is taken only from a plain file in its own folder, and its messages are shown as plain text. PDFs need `pypdf` in the engine (in `requirements-gis.txt`); a scanned PDF has no text to bring. The entry is read back as the context tools read it and removed if it doesn't read as a valid entry. Like every note it is served as information, not instruction, and with it the check `context.imported`: the text came from outside Columbus and may contain instructions, which an assistant must never follow; no assistant can change it (`update_notes` changes only notes about a connection). The CLI is `columbus-mcp notes import '{"file": "...", "preview": true}'`, then the same with `sha256` (from the preview, required), `kind`, `title`, `summary` and `when_to_use`; every preview, import and refusal is audited as `import_document`, which organization policy can deny. The app adds only the file last chosen in its own file dialog.

## Registry

`registry_search` and `registry_get` read the [geo-registry](https://github.com/wiatrek-kevin-s/geo-registry) index (`registry.sqlite`, full-text search), installed with `columbus-mcp registry update` (from the registry's rolling release, or `--from` a folder for offline installs) under `%ProgramData%\Columbus\registry`. The index is checked against its `index.sha256` when installed and again before each use; a damaged or altered index is refused. Entries are community-written, so results are marked untrusted and say which entries no person has reviewed yet. A search by area leaves out entries known not to cover it and lists those with no recorded extent last, marked as unchecked. `registry_fetch` downloads an entry's data into the workspace as a layer: OGC API Features collections and ArcGIS REST feature layers (paged, optionally within a lon/lat bbox, at most the read limit of features) and GeoJSON files. Because the entry is community-written, its URL must be HTTPS to a public address (checked after DNS, and that address is the one connected to), redirects are not followed, downloads are capped at 200 MB, and the download is parsed as JSON by the engine, never handed to GDAL. Hosts listed in policy `fetch_hosts` download without asking; any other host needs the person's approval, with the URL and the entry's licence on the card. Other access types (WMS, STAC, EPT, zip files) are not fetched yet. ArcGIS REST layers are read by the shared ArcGIS pager (the one `arcgis` connections use): it reads the layer's JSON first, then pages with `resultOffset`/`resultRecordCount` (at most 1,000 features a page, or the layer's `maxRecordCount` if lower), sorted by the layer's object-id field ascending (`orderByFields=<oid> ASC`), so the order is the same every time. It keeps going while the server says `exceededTransferLimit`, even after an empty page (an empty page moves the offset on by the page size asked for). A layer that reports `advancedQueryCapabilities.supportsPagination: false`, or reports no advanced query capabilities at all (servers before 10.3), is read with `returnIdsOnly` and then the ids, sorted ascending, in `objectIds` batches of the same size, sent by POST. HTTP 429 is retried at most 3 times, waiting as `Retry-After` says (at most 60 s, 1 s when it says nothing); after that, and for any other failure (an HTTP error, an ArcGIS `error` reply, a sign-in refusal, a non-JSON answer), the call fails with a plain message naming the service's host and what to do. Whenever paging stops before the server says the data is finished (at 500 pages, or at the limit with rows left), the result carries `fetch.truncated` (warn) and is marked truncated; the page that crosses the limit is cut to the limit. The provenance record lists every request (POST batches by their first and last object id), the bytes and SHA-256 the server sent, the features kept, and a `paging` summary (`offset` or `object_ids`, the order, the page count, and why it stopped: `complete`, `read_limit` or `page_cap`).


The app's **Registry** page (Data › Registry) searches the same index through Columbus itself: `columbus-mcp app query '{"tool": "registry_search", "args": {...}}'` (or `registry_get`; `registry query` is the same command) runs one call in process, under the same policy and audit, and prints its result and checks as JSON. The only other call it takes is `project_db` with `{"action": "list"}`, optionally with `"project": "<id>"` to list as that project's chats see it (the Projects page uses it); nothing else can be called that way. Its **Install the registry index** button runs `registry update`. Entries are shown as text, links included.
## Skills

[`skills/`](../skills) holds the GIS skills library (design section 7): fifteen Agent Skills, from `working-with-columbus` and `crs-and-datums` to `lidar-with-pdal` and `sop-conversion`, each giving general practice first and then the exact Columbus tools and checks to use. ## Companion window and desktop app

While any AI client works with Columbus, the person can watch the session in the companion window (design section 8): every layer and table it makes, with check results and provenance, on a MapLibre map and in an attribute table linked to the map, and the requests waiting for a decision. The window is the local Columbus page (127.0.0.1, the same server and protections as the approvals page) with its built UI installed beside the program in `ui/` ([app/ui](../app/ui)). Its data calls are read-only, behind the page's session token, and audited; it opens only files Columbus's own tools wrote, unchanged since. With the same token the page also tells the server what its map shows, for the assistant's `map_view` ([The assistant and the map](#the-assistant-and-the-map)): plain values the server checks, and nothing about web layers.

**The map page.** The map fills the page and white sheets float on it; the page is black and white, and colour belongs to the data. Framed in the app it has no header: a legend floats at the top right with the session's outputs (per row: a swatch that shows or hides the layer, in the colour it has on the map; its name; its row count), and the active one opens to show its rows, size and checks, **Table**, **Zoom to layer** and its details (checks, what it was made from, provenance). Under the outputs are **Street background**, **Web layers** and **Measure**. On its own (the browser page, a session's own window) the page has its own panel at the left: the session, its connections, the requests waiting for a decision, then the same outputs and controls. The table is a sheet over the map, closed until it is asked for; its head has the output, the rows shown, Previous and Next, **Zoom to selection** and a close button. The active output is drawn in the colour of the answer; the others rest in quiet colours that stay their own. The app tells the framed page how much of it is covered (`inset`, below); the page keeps what it shows clear of that part and pads the map by the same numbers, so every zoom centres in the part no sheet covers, and when a sheet opens or closes the map makes room. In the app's window nothing covers the frame (it has the body of the panel on the right to itself), so those numbers are zero. The street background's style is fetched by the page from the one host its policy allows and recoloured to paper and ink before the map gets it (`restyle` in [`app/ui/src/basemap.ts`](../app/ui/src/basemap.ts), unit-tested by `app/ui/e2e/unit.mjs`); if it cannot be had the paper stays, a notice shows and the switch goes off. No font is bundled: the page and the app use the system's own typeface.

The Columbus desktop app ([app/desktop](../app/desktop), Tauri) is one main window with three parts. At the left is a sidebar (264 px wide). In the middle is the chat, or the page of a place; a page keeps to a centred column (at most 880 px wide) with its title at the top. At the right is a panel that opens when the assistant makes something (**The panel on the right**, below). The app opens on a question in the middle of the window (*What do you want to know?*): a box to ask in, with the chat's project, model and thinking level under it, things to try, and a line when something waits for the person. Once something is asked, the chat takes the middle column, with its title at the top. When nothing is set up, first steps stand in for the question: add data, then two checks (an AI for the chat, the GIS engine); each can be skipped. Under them is how the assistant should work: **Work freely on copies** (recommended) or **Ask me before each script** ([above](#policy-keys-added-in-015-f-15)). There is no Home page (its old address opens the new chat).

The sidebar has, from the top: the Columbus mark and name, with a button that folds the sidebar to a rail of icons (56 px wide) and back; **New chat** and **Search** (Ctrl+K, or ⌘K on a Mac: chats by title and content, sessions, every page, and the person's connections, workflows and projects by name); seven places; **Recents**, the 16 most recent chats and sessions other AI apps run, newest first, a dot on each one that waits for the person, with **All chats** under them; and at the bottom **Settings**. The place the person is in is marked; while a chat is open, its row under Recents is marked instead. Whether the sidebar is folded is remembered (in the window's own storage, `columbus.sidebar`); until the person chooses, a window narrower than 1100 px starts with it folded. The places:

- **Chats**: the app's own chat and the saved chats, grouped by when they were last used, and in the same list the sessions other AI apps run, marked with the app's name, which open to show their tool calls from the audit log and their map. A footer chooses which project's chats show.
- **Projects**: the person's projects ([Projects and data groups](#projects-and-data-groups)), each with its instructions, the connections its chats may use, its files ([Project files](#project-files)) and **New chat in this project**.
- **Data**: what the assistant can reach, one row per connection (what it is, read only or read and write, the rule that matters), and where results can go (the export folders). A connection's own page says its rules in plain words and has **Change the rules**, **Test**, **Draft notes** and, for ArcGIS, **Sign in**. Pages inside Data: **Datasets** (per connection), **Data groups**, **Map layers**, **Project databases** and **Registry**. A line at its foot opens **Documentation**.
- **Documentation**: four tabs. **My notes** (the person's notes, with Mark reviewed), **Organization's pack** (the organization's context pack, read only), **Proposals** and **Import**. A note or a pack entry opens to read in the panel on the right.
- **Workflows**: what cannot run until the person reads it (proposed workflows and tools), what runs by itself (scheduled workflows), and what runs when asked (other workflows, and installed tools). It links to **Tools**.
- **Tools**: toolboxes (installed ones, Add tools, and a search over their tools; see [Toolboxes](#toolboxes)), then the person's own tools. **Skills** (the bundled skills, read only) is a page inside it.
- **Activity**: one page. **Waiting for you** (requests across sessions, and workflows and tools to read), then **History** (the audit log in plain words with the line as written under it, quick views, filters and Verify, and the exports).

**Settings** is one sheet over the page that is open, not a page of its own. When something was saved in it, the page under it is brought up to date as the sheet closes (a page the person has typed or chosen something on is left as it is). The model and thinking level set here are for new chats: a chat that has started keeps the ones it runs on, which are the ones its two boxes show. Its first view holds how the assistant works (**Work freely on copies** or **Ask me before each script**, with the mode in force), the assistant (API key, model and thinking level for new chats), Python (where scripts run, other environments), the map (street background, light or dark appearance) and this computer (where things are kept, whose policy is in force). Parts open inside it: **Assistant** (key, model, GIS engine), **Python environments**, **Privacy and files**, **Keyboard shortcuts** and **Organization rules** (the policy in force and its switches). The Workflows page says when schedules are not available on the system. The window offers only what works: the placeholders for parts Columbus has no backend for (Accounts and services, Work account and Agent app, organization and imported skills) were removed from it, and those features are still not built. Nothing in the window shows made-up data. Light and dark themes follow the system or the person's choice; the window is at least 1024 × 680. Earlier addresses still open the page that took their place (`#/connections` shows Data).

**Keyboard and screen readers.** Every control in the window and on the map page has a name a screen reader can say (its text, a label or an `aria-label`), and none is taken out of the Tab order; the desktop scripts and the map page's scripts assert both before every picture a passing run takes ([`app/ui/e2e/a11y.py`](../app/ui/e2e/a11y.py)). The document follows what is seen: the sidebar comes first, then the middle, then the panel on the right, and on the start the question comes before what to try. **Skip to content** moves the focus into the page. The focus goes to a page's title when a link is followed, back to the Settings button when the sheet closes (whether or not something was saved), and to the request when one brings the chat back. The edge between the chat and the panel takes the focus, and the left and right arrow keys then move it. Esc closes what is being read in the panel, then brings the chat back if the map fills the window; a key pressed while the focus is inside the map's frame goes to the map page, not to the window. Text is at least 4.5:1 against its background in both themes, fields and the off switch have a 3:1 edge, click targets are at least 24 px high or carry a label, the focus is always shown (a ring; in the search box and the message box, the caret, in a chat the message box's darker edge, and on the edge between the chat and the panel a line), and reduced motion is honoured. Not checked: what a particular screen reader says, and the map canvas itself, which has no text alternative beyond the table.

**Zoom to selection and Measure (REQ-28).** The map page has two tools, built from the map and table it already has. With **Zoom to selection** on (the default), clicking a row in the table fits the map to that feature (padding 60 px, no closer than zoom 18; a point zooms to 18); off, a click only selects and highlights the row's feature and the view stays where it is. The choice is remembered per chat: in the page's own storage under the session's id (`columbus.zoomToSelection.<session>`), so every window of that session, and the app's own view of it, keeps it while the session runs. A row the map does not hold (a layer cut off at its limit, a layer taken off the map) or without geometry leaves the view as it is. Clicking a feature on the map selects its row without moving the map. **Measure** measures a line drawn on the map: each click adds a point, a double-click finishes the line (the map does not zoom while measuring), the next click starts a new one (one result at a time), and Escape or pressing **Measure** again clears it and ends measuring; clicks while measuring never select features. The length is geodesic, on the WGS 84 ellipsoid (Vincenty's inverse formula, with the great-circle distance on the mean-radius sphere for nearly antipodal points), summed over the segments, and shown in feet first, then metres (`328 ft (100 m)`); 1 ft = 0.3048 m. Tested in a real browser against a real session by [`app/ui/e2e/map.py`](../app/ui/e2e/map.py), in CI's companion window job: row 2 of a three-route layer fits route 2, row 3 with the toggle off leaves the view unchanged, a second window of the session remembers the choice, and a line 100 m long measures 328 ft within 1%.

**The panel on the right.** Each chat or session shows its companion page (its map, results and table) in a frame that fills the body of a panel at the right of the window, beside the chat. The panel's head says **Map and table** and has four buttons: **Files this chat made**, **Open the map in its own window**, **Fill the window** (the middle is put away and the panel has the window beside the sidebar; the same button, then named **Show the chat again**, brings the chat back) and **Close the panel**. **Map**, in the chat's head, opens and closes the panel, and the chat's **⋯** menu has **Files this chat made**, **Fill the window with the map** and **Open the map in its own window**. The panel opens by itself the first time the assistant makes a result in the app's own chat; once the person closes it, it stays closed in that chat until they open it, or press **Table** on a result card. For a session another AI app runs it is open from the start, and a workflow run opened in a chat opens it on the table. The edge between the chat and the panel can be dragged, or moved with the left and right arrow keys when it has the focus, to resize the panel (it starts at 46% of the window's width, is never under 380 px, and leaves the middle at least 400 px); the width is remembered (`columbus.outputs`, in the window's own storage). In a window narrower than 1100 px the panel lies over the chat instead of beside it. The table is a sheet on the map: **Table** on a chat's result card opens the panel and asks the page to open it for that card's result (the layer the turn made, or the layer it exported). Things to read open in the same panel, over the map, each with its own title and close button in place of the panel's head: **Files** (**Files this chat made** lists the files in the session's workspace), **How it was made** (on a result card: that result's provenance record above the files), a script's code from an approval card, and a note or a pack entry from **Documentation**. Closing one shows the map again, or closes the panel if it was opened only for the reading. A request the app's own chat makes while the map fills the window brings the chat back by itself; one that already waits still counts in **Activity**, in the sidebar. The app gets the page from the session over the signed channel described under **Test** below (`POST /api/app-view`): the session hands a view link to its `/embed` page straight to the app, not through a `columbus://` link another program could catch. **Open the map in its own window** still asks for a window (`POST /api/open`) and opens it through a `columbus://` link: the server makes a fresh single-use launch token, and the app opens the session's page in a window of its own. Each server announces its port in `live/<session>.json`. Links handed to an app through a custom URL scheme can be intercepted by any program the person runs, so windows and frames opened for the app are view-only: their approval cards have the server open the browser page that can decide. A street background (OpenFreeMap) is off until the person turns it on, since tile requests reveal the area in view; policy `companion: { basemap: false }` removes the choice.

**Approvals in the app.** Under **Work freely on copies** a script that stays in the sandbox asks nothing; what crosses the boundary still asks. Requests from the app's own chat are answered in the chat, as any AI client answers its own session's prompts: a card (**Columbus needs your OK**) with **Allow once**, **Allow for this chat** where the server offers it, and **Decline**. **Allow for this chat** is the app's name for the server's "allow for this session" (for a script, **Allow this script for this chat**); the browser approvals page still says **Allow for this session**. The buttons wait a second; a script's code shows in its own box and can be read in the panel on the right. Requests from other AI apps are decided in that app's own prompt or on the browser approvals page, never in this app: **Activity**, under **Waiting for you**, and the session's own **Waiting for you** tray list them (summaries only, grouped by session and kind, with the time left), and **Decide in browser** asks the session to open its page (`POST /api/app-approvals`, signed, view only; the session limits how often it opens a page). **Activity** also lists the app's own chat's requests, with **Answer in the chat**, which goes to the chat. Deciding other apps' requests in the app, with Windows Hello or Touch ID, waits for a security review.

**What the main window can do, and why that is safe.** The main window holds the app's own chat, the connections and switches editor, the person's tools and the read-only views, so its capability ([capabilities/main.json](../app/desktop/src-tauri/capabilities/main.json)) grants those commands, to the app's own local pages only:
- Every change that gives the assistant more access is confirmed by the person at the keyboard in the app's Rust code (`settings.rs`, `confirm`), whichever window asks: the web page cannot skip it. The commands check their inputs as before; the read-only views read only Columbus's own folders, by relative path, refusing `..`, absolute paths and links out of them.
- Everything that comes from the AI, data, files or a session is shown as text (`textContent`, DOM nodes), never as markup; the only markup the page builds is its own fixed icons. A strict Content-Security-Policy (`tauri.conf.json`) allows the app's own scripts and styles only, no remote script, and frames only from `http://127.0.0.1`.
- The companion page in the panel on the right is another origin (`http://127.0.0.1:<port>/embed`) in an `<iframe sandbox="allow-scripts allow-same-origin">` (no top navigation, popups, forms or downloads). It cannot use the app's IPC: no capability names a remote origin (a unit test checks every capability file), Tauri judges each IPC request by its own origin (the frame's), and on macOS and Linux Tauri's scripts are not injected into frames at all. On Windows, wry injects Tauri's scripts into frames too (the frame does see `__TAURI__`), so there the barriers are Tauri's origin check, which refuses every command from the frame's origin, and WebView2 handing a frame's messages to the frame's own handler, which the app does not listen to; a test on all three systems in CI ([`frame_ipc.py`](../app/desktop/e2e/frame_ipc.py)) puts a page in the main window's frame that tries `__TAURI_INTERNALS__.invoke`, `window.ipc.postMessage`, `chrome.webview.postMessage` and the IPC addresses directly, for a read and for changes (a connection, with the confirmation stand-in set to allow, and the app's preferences), and checks every one is refused or unanswered and nothing changed. Residual, for IPC through frames on Windows: those two barriers are Tauri's and WebView2's, not the app's. The main window's navigation guard and its CSP (`frame-src http://127.0.0.1:*/embed`) let the frame load only the `/embed` page of sessions that handed the app a link. The server lets only the app's own origins frame `/embed`, and nothing else: `/`, which an approve link opens, keeps `frame-ancestors 'none'` and `X-Frame-Options: DENY`. A framed page never decides approvals, whatever its link.
- The app and the framed page pass each other only short messages of plain values, and each side takes a message only from the other (its window and its origin are checked). The app sends `columbus-embed` with `basemap` and `theme` (the person's choices), `inset` (how many CSS pixels of each edge of the frame are covered; plain numbers, so the page can keep its controls clear of them; nothing in the app's window covers the frame, so all four are 0), `shown` (true or false: whether the panel on the right is open with this map in it, which the page uses only to know whether it is in front of the person, for [`map_view`](#the-assistant-and-the-map)) and, when the person asks for the table from a chat or opens a workflow run in a chat, `view: "table"`; with it, from a result card, `output` (that result's workspace handle: a plain id, which the page takes only if it equals the handle of one of its own session's outputs that has rows, `namedOutput` in [`app/ui/src/layout.ts`](../app/ui/src/layout.ts); any other value changes nothing). After a web layer is saved or removed it sends `columbus-web-layers`. The page sends only `columbus-embed-ready` and `columbus-add-web-layer`, which carry nothing else.
- The program the app's chat starts is checked each time: a file named `columbus-mcp` (`columbus-mcp.exe`), by its full path, outside the workspaces, notes and chats folders. It is the server that comes with the app, or else the one in the person's Columbus folder; no setting names another. The GIS engine it runs can be chosen (Settings › Assistant), and choosing one is confirmed at the keyboard like any widening change.
- "Mark reviewed" marks exactly the note the person read: the window gets the SHA-256 of the note's bytes with its text, the app refuses if the file changed since (or is too large to show whole), and only the word `draft` on the front matter's `status:` line changes.
- The API key can be set or cleared but never read back by any page. Chats are saved as plain files in the app's data folder, on this computer only.

The classic session list and settings window stay reachable from **Classic windows**, at the foot of the Settings sheet, until the main window has proved itself; the classic chat window is retired (its chat is the main window's, and the app runs one chat at a time).

**Settings apply without a restart.** Every call re-reads the policy and connection files if they changed (hashing exactly the bytes it parses, regular files only), once the change has settled: every file untouched for a second by its times (checked again after reading), or the same contents seen again a second later, so a file being saved in place is never used half-written; files that keep changing for ten seconds stop every tool until they keep still. The new settings apply from that call on: a removed connection, a switch turned off or a tighter filter take effect at once, and anything looser only after the app's confirmation, as above. On every change, caches learned under the old settings are not reused, every approval not yet used and every "allow for this session" is withdrawn (the person is asked again), a change set from `propose_edits` is refused by `apply_edits` (propose again), and an approval given while the settings changed is not used. When a change narrows what a connection allows (removed, its type no longer allowed, or anything about it changed but its description and mode), workspace files carrying that connection's data label are removed and no tool will open them; a newly hidden field removes every file with governed data. Labels are conservative: a file made after the session read a connection carries its label. Every reload is an audit line (`settings.reload`) naming what it withdrew and removed. Files that do not load, a policy file that goes missing or is emptied once one has been in force (never a fall back to the defaults), or a change to what only a start applies (`servers`, `plugins`, `hosts`) stop every tool but `whoami`, which then starts and connects nothing, until fixed or until the AI app is restarted: a session never runs on half old, half new settings. Hand edits to the files behave the same way. The person's own tools are read again live too, on their own approvals ([Personal tools](#personal-tools)). A call that was running when a narrowing applied (including fewer rows or seconds allowed, by the values in effect) has its answer withheld (it may hold rows) and the files it made withdrawn (a change of limits alone removes no files); a write it already committed to a source, or an export already in its folder, is said plainly. An approval given while a change to the files is still settling is not used. An empty policy file is refused at start, too. Limits: exports already written stay where they were written, and a file that cannot be deleted at once (held open on Windows) is withdrawn from every tool and deleted at the next reload.

**Test** in the connection editor asks a running session that reads the same connections folder to open the connection as the form describes it, before saving (**Test** on a connection's own page does the same for the saved connection): the organization's policy is applied, the engine lists the datasets, and the connection's allow and deny lists are applied to them. Nothing is saved and the AI sees none of it; each test is an audit line (`settings.test_connection`, client `columbus-app (settings)`) with where it pointed and whether a typed, stored or no password was used. Each session writes a random key to `live/<session>.key`, a file only this account can read (its `live/<session>.json` is private too). The key is never sent: the app sends a fresh challenge signed with the key (`POST /api/test-hello`), so only a key holder can ask for one, checks the session's HMAC-SHA256 answer, so a program that merely took over a port gets nothing, and then sends the test (`POST /api/test-connection`) with its own HMAC over the method, the path, the session's single-use challenge and the exact request body, so a proof made for one endpoint is refused by every other (the same holds for `/api/draft-notes`, `/api/app-view` and `/api/app-approvals`). Requests with any `Origin` header or another host name are refused, so no web page, this session's own included, can send one. A password typed in the form goes only to that session's engine; with none typed, the stored password is used only when the form points where the saved connection of that name already does (same type, host, port, database, login, DSN, path), and the saved connection's own dataset lists then apply too. A host name with a list, path or option characters (`,`, `;`, `/`, `@`, spaces…) is refused for every connection; SQL Server may name one instance (`db01\SQLEXPRESS`), checked against `hosts` by its host part. An Oracle `dsn` is checked like a host: an EZConnect string (`db.corp:1521/svc`) by its host, a full connect descriptor is refused, and a bare alias (`ORAPROD`) is looked up in the `tnsnames.ora` that `TNS_ADMIN` or `ORACLE_HOME` points to, whose hosts are not checked against `hosts` (so that file is the control for aliases). An EZConnect string must be exactly one address with a service: `[tcp://|tcps://][//]host[:port]/service[:server][/instance]`; a second address after `;`, options or anything else is refused. A name with no `/service` (`PROD.WORLD`, even `db.corp:1521`) is what the driver looks up in `tnsnames.ora`, so it counts as an alias.

**Folders of files and ArcGIS services in the app** (T-12, REQ-11). The connection editor (**Add data** under Data, or **Change the rules** on a connection's page) adds and edits `files` and `arcgis` connections with the same form and checks as every other type (existing components only): for **Folder of files**, the location (a folder, or one file typed in), **Read subfolders too** (`recursive`), the coordinate system (`crs`) and the X and Y columns (`x`, `y`), all kept when the connection is edited again; for **ArcGIS service**, the service address (`url`), **Sign-in** (none, or ArcGIS OAuth with the **Portal** and the organization's **Client id**, D-12) and **Features per page** (`page_size`). Both are read only, take no password, and are checked by the server's own connection rules before saving (an `http://` address, a missing portal, x without y or a CRS that is not `EPSG:<code>` are refused in plain words). Saving a new one, or a changed address, portal or other setting, is confirmed at the keyboard like any connection. **Test** works for both: a public service needs no sign-in, and a service that does not answer gives the plain R-14 message ("ArcGIS service at <host> could not be reached. Check the address or your network, then Test again."). An ArcGIS connection that signs in has a **Sign in** button on its page: after the person confirms at the keyboard (Touch ID, password or Windows Hello), the app runs its own Columbus server's `columbus-mcp arcgis signin <id>` with `COLUMBUS_SIGNIN_BROWSER=print`, opens the sign-in address it prints in the person's browser (only an `https` address under the connection's portal ending in `/oauth2/authorize`; in test builds with `COLUMBUS_FETCH_TEST_LOOPBACK`, `http` to 127.0.0.1 too) and waits up to 7 minutes for the browser to come back; the tokens go from that program to the credential store, never through the app or its page, which shows only the outcome ("Signed in as … for <id>.") or the plain error (a portal that does not answer gives its R-14 message; a browser that did not come back says to press Sign in again or to use `--paste-code` in a terminal). One sign-in runs at a time. Draft notes is not offered for ArcGIS services. With no credential store (Linux), sign-in is refused as in the terminal (R-17).

The app also has its own chat ([crates/chat](../crates/chat)), in the main window: the person adds an Anthropic API key (kept in the operating system's credential store and never given to a web page), and the chat starts its own Columbus session and gives the model that session's tools and nothing else. Approvals come to the chat as prompts written by the app, not the model, through MCP elicitation, the same route as in Claude desktop. Tool steps fold into one line per turn ("3 steps · …") that opens to show each step, with check badges and, for results that made data, a **Provenance** link. The last result of a turn is a card with **Table** (opens the table on the map) and **How it was made**; that and **Provenance** open the result's record in the panel on the right. Under the message box are the chat's project (it can be chosen until the first message), its model and its thinking level. Each chat's transcript is saved in the app's data folder (`chats/<id>.jsonl`), listed under **Chats** and searched by title and content; an ended chat reads back but cannot be continued.

## Connections and secrets

Each connection is one YAML file the person adds (see [`examples/connections`](../examples/connections): `crash-files.yaml` is a folder of files, `roads-agol.yaml` a public and `row-polygons.yaml` a signed-in ArcGIS service); the agent has no tool to add or change one. columbus-mcp secret set gis-postgis      # prompts twice, nothing echoed


A connection with no stored secret uses integrated sign-in. The gateway reads the secret only to open a connection, hands it to the engine worker inside that one request, and never returns it to the agent; worker error messages are scrubbed of it. `whoami` reports which secret store is in use.

### ArcGIS connections

An `arcgis` connection (build brief Part 4, AF-1, REQ-8, REQ-9) reads one service, or one layer in it, over the ArcGIS REST API. **The gateway makes every request itself**, in Rust, with the same HTTP client `registry_fetch` uses; the engine and the agent never talk to the service.

- **Host rule.** The service's host (and a signed-in connection's portal host) must be on policy `hosts` before any request is sent; otherwise every tool refuses the connection ("host … is not on the organization's allowed host list"), and Test in the app says so. The URL is read twice, by the policy layer and by the HTTP client's own parser, and a URL the two read as different hosts is refused. Each tool call resolves the host once and connects only to that address (pinned, as `registry_fetch` does), follows no redirect (a moved service says to put its new address in `url`), sends nothing to any other host, and waits at most 30 s for any request. Private addresses are allowed (ArcGIS Enterprise usually is one): the host list is the rule. Plain `http://` is never used, except to `127.0.0.1` in test builds with `COLUMBUS_FETCH_TEST_LOOPBACK` set (a portal may then also be `http://localhost`).
- **Datasets (F-1b).** Every layer and table of the service (from `<service>/layers?f=json`, or the one layer its URL names) is a dataset under its published name; when two share a name (compared case-insensitively), each is `<name>_<layer id>` (`Signs_3`). Group and raster layers aren't offered. The allow and deny lists match these names.
- **`list_datasets`, `describe_dataset`, `sample_rows`** read the layer's JSON: fields (with alias, length and coded-value or range domains), the geometry type (`LineString M`, `Point`, … with `esri_geometry_type`, `has_z`, `has_m`), the spatial reference (`crs`: `code` `EPSG:<latestWkid>`, `wkid`, `latest_wkid`, plus the engine's CRS facts in `describe_dataset`), the extent (left out under a row filter, as for every source), `layer_id`, `object_id_field` and `max_record_count`; a table has no geometry. `describe_dataset`'s `rows` is the service's own count (`returnCountOnly`) under the row filter. Hidden fields are removed from all of these. The layer list is reused for up to 5 minutes within a session.
- **`query_features`** asks for `f=json` (Esri JSON), with `returnZ` and `returnM` when the layer has them, so Z and M values survive into the workspace layer (AF-17). Fields become `outFields`, by name, never `*`, with hidden fields refused; the geometry always comes with a layer. The `where` sent is the connection's row filter (and any data-group filter), each in parentheses, ANDed with the caller's `where`: `row_filter: "DISTRICT = 14"` and `where: "LANES > 2"` send `(DISTRICT = 14) AND (LANES > 2)`; with neither, `1=1`. A `bbox` becomes an envelope (`geometryType=esriGeometryEnvelope`, `spatialRel=esriSpatialRelIntersects`) with `inSR` from `bbox_crs` (`EPSG:<code>`) or the layer's own wkid; `order_by` (one field) becomes `orderByFields <field> ASC`, and the shared pager adds the object-id field so the order is total (Part 3). Pages are read by the shared pager (it goes on past an empty page while the service says `exceededTransferLimit`, falls back to object-id batches where the layer cannot page, and retries HTTP 429 at most 3 times, honouring `Retry-After`). The read limit counts features across pages: the page that crosses it is cut and the result is marked `query.read_limit` (R-11; a 250,000-row layer under a 200,000-row limit gives 200,000 rows and the warning). The gateway removes every attribute it did not ask for from each page before the engine sees it (a service that sends a hidden field anyway gets it dropped), then the engine turns the pages into the workspace layer with GDAL's ESRIJSON driver only, keeping M (`esrijson_layer`). `sample_rows` reads the first rows the same way, writing nothing. `executed_sql` and the provenance record say what was asked: the layer, the `where`, `outFields`, `orderByFields`, the envelope, the paging and each page's request, size and SHA-256 (requests never carry a token: a signed-in connection's token goes only in the `Authorization` and `X-Esri-Authorization` headers, never in a URL, form or record). Reads label the session with the connection, and are audited, as for any connection.
- **The `where` is rebuilt, never passed through (R-10, R-10b).** The caller's `where` is parsed with the `query_features` where parser (comparisons, AND/OR/NOT, IN, LIKE, BETWEEN, IS NULL, `UPPER`/`LOWER`/`TRIM`/`SUBSTR`, CAST; no subqueries) and written back out from the parse, every name replaced by the layer field it means, as the layer publishes it; a name the layer lacks or a qualified name (`t.x`) is refused. Before any request is sent, a `where` outside that subset, and a hidden field in `fields`, `where` or `order_by`, are refused ("SSN is hidden by organization policy…"); so is input such as `1=1) OR (1=1`, which does not parse, so it cannot escape the parentheses. The row filter is parsed the same way when the connection is loaded, and a connection whose row filter doesn't parse is refused then; at each request it is rebuilt against the layer's fields, and a dataset whose fields don't fit it (a name it lacks) is refused rather than read unfiltered. Counts (`returnCountOnly`) carry the same rebuilt filter, so a hidden field can't be inferred through them.
- **`sql_select`** is refused with `query.unsupported` and the fix "use query_features" (R-12): a service takes no SQL. Edits, engine plugin extracts and drafted notes don't apply to `arcgis` connections.
- **Plain failures (R-14).** Every failure names the cause and the fix: "ArcGIS service at services.example.com did not answer in 30 s. Check the address or your network, then Test again."; could not be found or reached; answered with a redirect; answered HTTP <n>; refused the query ("<the service's message>"); needs a valid sign-in (HTTP 401/403, codes 498/499: "Sign in again, or check that the layer is shared with you"); is limiting requests (HTTP 429) and still refused after 3 retries; did not answer with JSON.

### ArcGIS sign-in

A connection with `auth: {type: oauth, portal, client_id}` (F-3) reads a service only once the person has signed in (T-11; build brief Part 4, D-4, D-12, REQ-10, R-17, R-18). Columbus ships no client id: each organization registers its own ArcGIS OAuth app and puts its client id in the connection (D-12; `docs/manual-checks.md` gives the admin steps). The app's redirect URIs must include **both** `http://127.0.0.1` (the default; Columbus adds a random port) and `urn:ietf:wg:oauth:2.0:oob` (the paste-code fallback). Columbus stores no password (Security baseline item 6).

```powershell
columbus-mcp arcgis signin roads-agol               # in the browser; the redirect comes back to Columbus
columbus-mcp arcgis signin roads-agol --paste-code  # the portal shows a code; paste it into this terminal
columbus-mcp arcgis signout roads-agol              # remove the sign-in
```

- **Signing in.** Authorization code with PKCE (S256, a fresh 64-character verifier each time) at `<portal>/sharing/rest/oauth2/authorize`, the code exchanged at `<portal>/sharing/rest/oauth2/token` (`<portal>` without a trailing `/sharing/rest`, which is dropped if written). Run at the keyboard, never by an agent: no MCP tool signs in. The browser opens the portal's page (the address is printed too). By default the redirect is `http://127.0.0.1:<random port>`, answered by a listener on 127.0.0.1 only that accepts one redirect to `/` with this sign-in's `state` (any other `state` ends the sign-in, nothing stored) and closes after it or after 5 minutes. With `--paste-code`, or when the browser has not come back (press Enter at any time, or wait for the 5 minutes), Columbus starts again with the redirect `urn:ietf:wg:oauth:2.0:oob`: the portal shows a code, which the person pastes into the terminal prompt (never into a chat); only letters, digits and `-._~` are taken. The command prints the outcome and the ArcGIS user name, never a token or code.
- **The credential entry (F-3b).** The tokens go only into the OS credential store (Windows Credential Manager, the macOS Keychain; service `columbus`), entry `arcgis:<connection id>`, as JSON `{access_token, refresh_token, expires_at (ISO 8601, UTC), portal}`. It is never logged. Signing in again replaces it.
- **No credential store (R-17).** Without one (Linux today, or development mode without a folder), `arcgis signin` is refused with "ArcGIS sign-in refused: there is no credential store on this system, so Columbus cannot keep an ArcGIS sign-in (it never writes tokens to files). Public layers (auth: none) still work.", and a signed-in connection's reads say the same; public connections work as before. Tokens are never written to a file; the one exception is debug builds with `COLUMBUS_DEV_SECRETS=1` and `COLUMBUS_DEV_SECRETS_DIR`, for tests.
- **Using it.** Each call reads the entry. An access token that has ended (or ends within a minute) is refreshed once, without asking (`grant_type=refresh_token`), and the new one stored; two calls at once refresh once. A refresh token the portal refuses (expired or revoked; ArcGIS's last about two weeks, as the organization sets) gives exactly "<id>'s ArcGIS sign-in has expired. Sign in again: columbus-mcp arcgis signin <id>", and nothing goes to the service. Before anyone has signed in: "<id> needs an ArcGIS sign-in, and nobody has signed in yet. Sign in: columbus-mcp arcgis signin <id>". A stored sign-in for another portal than the connection now names is not used ("Sign in again: …"). The token is sent only as the `Authorization: Bearer` and `X-Esri-Authorization` headers, for the layer list, counts, layer JSON and every page; it never reaches the agent, the engine, the audit log, provenance, tool results or error messages.
- **Which hosts get the token (R-18).** The portal itself, and a service host the portal vouches for: the portal's own host; `services*.arcgis.com` (`services.arcgis.com`, `services1.arcgis.com`, …) when the portal is `www.arcgis.com`; or a host of a server the portal lists as federated (`<portal>/sharing/rest/portals/self/servers`, the `url` and `adminUrl` of each, asked with the token and reused for 5 minutes). Any other host gets the request without the token; if it answers that it needs one (HTTP 401/403, codes 498/499), the call is refused with "the portal does not vouch for <host>, so Columbus will not send it your sign-in, and <host> needs one. Fix: …". If the portal cannot list its servers, it vouches for none.
- **In the app.** The **Sign in** button on the connection's page (under Data) runs the same sign-in after the person confirms at the keyboard (see [Folders of files and ArcGIS services in the app](#companion-window-and-desktop-app)).
- **When the refresh token ends.** F-3b's entry has no room for it, so Columbus keeps it apart, in an internal, non-secret file beside the connection files: `connections/.arcgis-state.json`, `{"<id>": {"refresh_expires_at" (ISO 8601, UTC), "portal"}}`, never a token. Sign-in writes it from the portal's `refresh_token_expires_in`, and each exchange (above, in [Workflows](#workflows)) again. A missing, unreadable or other-portal line counts as not known, and the next workflow step exchanges (the safe side). Like `environments/.confirmed.json`, no MCP tool writes the connections folder and confined scripts can't write outside their run folder. Connection loading reads only `.yaml`/`.yml` files there, so the file never counts as a settings change.
- **Signing out.** `columbus-mcp arcgis signout <id>` deletes the entry and its line in `.arcgis-state.json`. Deleting an `arcgis` connection deletes its entry and its `.arcgis-state.json` line too (F-3b): a running session does so when it sees the connection gone, and the app's **Remove** (in the connection editor) does at once. `whoami`'s connection card for a signed-in connection says `signed_in: true` or `false` (whether an entry is stored; never the token).

For development and CI only, `COLUMBUS_DEV_SECRETS=1` reads passwords from `COLUMBUS_SECRET_<ID>` environment variables instead; `whoami` flags it. Passwords are kept in Windows Credential Manager or the macOS Keychain; Linux has no credential store yet, so there only this mode works (and ArcGIS sign-in is refused, R-17).

### Web map layers (server side)

Display-only layers on the person's map (build brief part 2, Part 3; AF-22, REQ-31, REQ-32, REQ-34, D-14): XYZ tiles, WMTS, WMS, ArcGIS MapServer and ImageServer (cached tiles, or a dynamic `export`/`exportImage` per tile), and ArcGIS feature layers drawn as vectors. The app's side (the Map layers page, the layer list, the privacy notice) is T-25; this is what the gateway does (`crates/gateway/src/web_layers.rs`, formats in `crates/shared/src/map_sources.rs`).

- **Saved sources (F-13).** One file per layer, `map-sources/<id>.yaml` beside the `connections` folder (`COLUMBUS_MAP_SOURCES` overrides): `id` (letters, digits, `-`, `_`; at most 64), `title`, `kind` (`xyz`, `wmts`, `wms`, `arcgis-map`, `arcgis-image`, `arcgis-features`), `url` (https), `layer` (WMS or WMTS layer name, or ArcGIS layer number), `auth_from` (an `arcgis` connection id), `attribution`. Unknown keys are refused. Columbus also requires: an XYZ `url` with `{z}`, `{x}` and `{y}` and no other placeholder (no `{s}` subdomains); a `layer` for WMS and WMTS, and for a feature layer whose URL names no layer number; `layer` a number for ArcGIS kinds; `auth_from` only on ArcGIS kinds. One unreadable file is skipped with a note; the others still load. The organization can supply sources in policy `map.sources` (same entries); a saved source with the same id is not used.
- **Policy (F-14).** `map: { allow_web_layers, hosts, sources }`; unknown keys refused. `allow_web_layers` (default true) false refuses every web-layer request and empties the lists. `hosts` (`*` wildcards, as policy `hosts`): when listed, every host any web-layer request goes to must match it, and `map-source inspect`/`save` refuse any other host, naming it. When empty, a source's own `url` host is allowed (the person saved the source at the keyboard, or the organization listed it), and any other host the service's capabilities name (a WMTS `ResourceURL` or KVP `GetTile` host, a WMS `GetMap` `OnlineResource` host) only if it was recorded as approved when the person saved that source: `map-sources/.hosts.json`, `{"<id>": {"url", "hosts"}}` (non-secret; F-13 gains no key; a changed `url` voids the record). Policy sources get no such record, so with `map.hosts` empty their capability hosts must be the source's own. ArcGIS `tileServers` subdomains are never used: tiles come from the service's own host.
- **The proxy (D-14).** On the session's companion page server (127.0.0.1), with the page's session token as `Authorization: Bearer` (the header MapLibre's `transformRequest` adds; never in the URL), like every `/api` call; no token, a wrong one or a wrong `Host` is refused (401/403) before anything is read. The page names a source id and a tile or an extent, never an address: any `/api/web/…` path other than the four below, or a query with `url=`, `href=`, `src=`, `template=` or `://`, is refused with 400 "web layers are named by a saved layer's id, never by an address…", and nothing is fetched.
  - `GET /api/web/sources`: `{enabled, sources: [{id, title, kind, raster, attribution, secured, origin: "saved"|"policy", rev}], notes}`; no URLs or hosts. `rev` is the first 12 hex digits of the source's fingerprint (kind, url, layer, auth_from): it changes on an Edit, so the map draws the layer afresh (T-25). Re-reads the settings first, and drops the cache folders of sources that no longer exist.
  - `GET /api/web/source/{id}`: `{id, title, kind, raster, attribution, secured, extent: [w,s,e,n] in degrees or null, min_zoom, max_zoom}` plus, for raster kinds, `tiles: "/api/web/tile/{id}/{z}/{x}/{y}"` and `tile_size: 256`, or, for feature layers, `features: "/api/web/features/{id}"`, `max_features: 5000`, `fields` (hidden ones left out) and `geometry_type`. Reads the service's capabilities (kept 5 minutes).
  - `GET /api/web/tile/{id}/{z}/{x}/{y}`: one 256 px Web Mercator (EPSG:3857) tile, `z` 0–24, as the service's image bytes and content type (`image/*` only). XYZ: the template; WMTS: the layer's TileMatrix whose scale is that zoom's (a GoogleMapsCompatible/EPSG:3857 set, 256 px, world top-left origin), `{TileMatrix}/{TileRow}/{TileCol}` filled; WMS: `GetMap` (1.3.0 `CRS` or 1.1.1 `SRS` `EPSG:3857`, the tile's box, 256×256, PNG preferred, transparent) for a layer offered in EPSG:3857 (or 900913), its CRS inherited from parent layers; ArcGIS: `/tile/{level}/{y}/{x}` when the service is a single fused cache in Web Mercator with no `layer` chosen, else `export` (`layers=show:<layer>`) or `exportImage`, `bboxSR`/`imageSR` 3857. Errors are `{error}` with 400, 401 (sign-in needed), 403 (host refused, or not vouched), 404 (no such source or tile) or 502 (the service failed, R-14 wording).
  - `GET /api/web/features/{id}?bbox=w,s,e,n` (degrees): the view's features as GeoJSON, `{type: FeatureCollection, features, total, exceeded}`: a `returnCountOnly` first, then pages of `f=geojson` (`outSR=4326`, page size the layer's `maxRecordCount`, at most 2,000; paged with `resultOffset` when the layer supports it) up to 5,000; `exceeded` is true past that ("Zoom in to see all"). When the layer comes through an `arcgis` connection (`auth_from`), fields matching policy `hide_fields` are neither asked for (`outFields`) nor passed on.
- **Transport.** Like `fetch_tools.rs` and `arcgis.rs`: each host's addresses resolved once and pinned (kept 5 minutes); an address on this computer, link-local, unspecified, broadcast or multicast is refused (private networks are allowed: organizations serve imagery internally); https only; no redirects ("…answered with a redirect, which Columbus does not follow…"); 30 s per request; answers capped (16 MB per image, 32 MB per capabilities document, 64 MB per feature page); HTTP 429 retried at most 3 times after `Retry-After` (up to 10 s), then R-14. Only the image or GeoJSON bytes and the content type go back to the page; no service header is passed on. Test builds with `COLUMBUS_FETCH_TEST_LOOPBACK` also accept plain http to `127.0.0.1`, `localhost` and the names in `COLUMBUS_WEB_TEST_HOSTS`, which then stand for 127.0.0.1 (release builds never do).
- **ArcGIS sign-in (R-18).** A source with `auth_from` gets that `arcgis` connection's access token (read and refreshed as for the connection itself, [ArcGIS sign-in](#arcgis-sign-in)), as `Authorization: Bearer` and `X-Esri-Authorization`, only on requests to a host the connection's portal vouches for (its own host, `services*.arcgis.com` for `www.arcgis.com`, or a federated server); any other host gets the request without it, and an answer asking for a sign-in is refused with "the portal does not vouch for <host>…". Not signed in: 401 with "Sign in: columbus-mcp arcgis signin <id>". An answer that contains the token is not passed on. Tokens never reach the page, the agent, the cache's names or any message.
- **Tile cache.** `<workspaces root>/cache/tiles/<source id>/<z>_<x>_<y>.<png|jpg|webp|gif>`, with `.source` holding the source's fingerprint (kind, url, layer, auth_from): a changed source's tiles are dropped at the next write and never served. At most 500 MB for all sources together: past it, the oldest tiles (by write time) go until under 450 MB. A source's folder is deleted when it is removed (`map-source remove`, or at the next `/api/web/sources` when its file is gone) or changed by `map-source save`; a secured source's also when its `arcgis` connection signs out or is deleted (`arcgis_auth::sign_out`, the one sign-out path, used by `arcgis signout` and by a session seeing the connection gone), and before any reuse while `arcgis_auth::signed_in` is false (a sign-in deleted elsewhere). Feature answers are not cached.
- **The app's commands** (`columbus-mcp map-source …`; JSON on stdout, exit 1 with `{ok: false, message}` on refusal; never MCP tools):
  - `inspect URL [--kind K] [--auth-from CONNECTION]`: guesses the kind from the URL when not given (`{z}` → xyz; `…/FeatureServer[/n]`, `…/MapServer`, `…/ImageServer`; `wmts`; `wms`), checks `allow_web_layers` and `map.hosts`, reads the capabilities from the pasted host only, and returns `{ok, kind, url, host, layers: [{layer, title, hosts, refused_hosts}], confirm}`. `hosts` are the other hosts drawing that layer would reach; `refused_hosts` those `map.hosts` refuses; `confirm` is true when `map.hosts` is empty, meaning the app must have the person confirm at the keyboard (`settings.rs` `confirm`, naming the host and any capability hosts) before saving. WMS layers not offered in EPSG:3857 and WMTS layers without a Web Mercator 256 px set are not offered.
  - `save JSON|- [--replace]`: the F-13 entry (JSON, or `-` for stdin); refused if the id is the organization's, exists (without `--replace`) or doesn't (with it), `auth_from` isn't an `arcgis` connection, a host is off `map.hosts`, or the capabilities can't be read or lack the layer. Writes the file atomically, records the chosen layer's capability hosts as approved when `map.hosts` is empty, and drops the cache if the source changed. Returns `{ok, id, file, hosts}`.
  - `test ID`: asks as the map would (one tile at the lowest zoom, or a feature count) and returns `{ok, message}` ("reachable: …", or the R-14 wording).
  - `remove ID`: deletes the file, its approved-hosts record and its tile cache (not for policy sources).
  - `list`: `{ok, allow_web_layers, hosts, confirm, sources: [F-13 fields + origin + approved_hosts], notes}`.
- **No agent access (D-14, REQ-34).** No MCP tool adds, changes, turns on or reads web layers, and none takes a source, URL or `auth_from`. They are not workspace layers: `list_outputs` doesn't list them, `map_snapshot` stays geometry only (no basemap, nothing downloaded), `map_view` reports and changes the session's own layers only (the page's report has no place for web layers, and the server refuses one that names any), and nothing about them goes to the AI provider. `whoami` lists `web_layers`: their titles, nothing more (empty when `allow_web_layers` is false).

### Web map layers in the app (T-25)

The person's side of web layers (REQ-31, REQ-33, R-21), using the server side above.

- **Data › Map layers** (`app/desktop/ui/js/pages/maplayers.js`, commands in `app/desktop/src-tauri/src/maplayers.rs`; main window only). **Add web layer**: paste an address, **Read layers** runs `map-source inspect` and offers the service's layers (an ArcGIS MapServer also offers "All layers (as published)", which draws its cached tiles; tile hosts a WMTS names are shown beside its layers), then Title, Name (id), Sign in through (an `arcgis` connection, for secured ArcGIS services) and Attribution. **Save** (`map_layer_save`) reads the capabilities again in the app's own code (never trusting the page), and when `inspect` says `confirm` (no `map.hosts`) asks Touch ID, the Mac password or Windows Hello (`settings::confirm`; debug builds: `COLUMBUS_APP_TEST_CONFIRM`), naming the service's host and the chosen layer's capability hosts, then runs `map-source save` (`--replace` for an Edit). An Edit that keeps to the layer's own host and its already-approved hosts is not asked again. Declined: nothing is saved ("not confirmed"). Each listed layer has **Test** (`map-source test`: "Reachable: …" or the R-14 message) and, for the person's own, **Edit** and **Remove** (`map-source remove`, no confirmation); organization layers are marked and can only be tested. Services needing a user name and password are not supported.
- **On the map** (`app/ui/src/WebLayers.tsx`, `MapView.tsx`): a **Web layers** button (in the legend, or in the page's own panel in a browser) opens the list of every saved and organization layer (`/api/web/sources`, read again every 5 s, on focus, and when the app says a layer changed). Each starts **off**. Per layer: on/off, opacity (0–100 %), Up/Down (the list is top first; the top one draws above the others; all web layers draw below the session's own layers), **Zoom to layer** (the extent `/api/web/source/{id}` gives). **Basemap**: Streets (when policy allows it), None, or any raster web layer, which then draws at the bottom at full opacity instead of the street basemap. The first web layer turned on (or chosen as basemap) in a chat shows, once per chat: "Web layers' services see which area you're viewing." All of this is kept per chat in the window's storage (`columbus.web.<session>`, like Zoom to selection), so another window of the same chat keeps it and another chat starts with everything off.
- **Drawing.** Raster kinds are MapLibre raster sources on `<this server>/api/web/tile/{id}/{z}/{x}/{y}`; MapLibre's `transformRequest` adds the session token as `Authorization: Bearer` only to this server's `/api/web/` addresses. ArcGIS feature layers are fetched for the current view (`/api/web/features/{id}?bbox=…`, after each move) and drawn as vectors, at most 5,000; past that the row says "Showing 5,000 of N features. Zoom in to see all." Clicking a feature shows its attributes (hidden fields already removed by the server). A service that fails shows the server's message (R-14) on its row; the map and the other layers carry on. A web layer's 401/403/502 never signs the window out; only the session's own refusals do.
- **Add web layer on the map.** In the app, where the map page is framed in the panel on the right, the map's **Add web layer** asks the app (a `columbus-add-web-layer` message to the frame's parent, which carries nothing else) to open the same dialog; after any save or remove the app tells each chat's map frame (`columbus-web-layers`) to read its list again. In a browser window it says to add layers in the app (there, that is under Data › Map layers).
- **Content policy.** The map page's policy is unchanged: `connect-src`/`img-src` are `'self'` (the gateway's 127.0.0.1 origin) plus the existing street basemap host `https://tiles.openfreemap.org` when policy allows the basemap. Every web-layer request goes to the gateway; a request from the page straight to a service host is blocked by the policy (checked in `app/ui/e2e/weblayers.py`).

## Sync with GitHub and Gitea

A project's files folder (`projects/<id>/files/`, F-17) can sync with one repository on GitHub, a GitHub Enterprise Server, a Gitea or a Forgejo (D-20, REQ-42, REQ-43): get colleagues' changes, send your own, see what changed. Columbus talks to the server's web API with a token the person pastes into the app ([crates/sync](../crates/sync)). There is no Git program and no Git library in it, so it works on a PC without Git, and nothing from a repository can run on the PC: no hooks, no Git configuration, no submodules. The assistant has no part in it: nothing here is a tool. No file is ever sent unless the person presses **Sync**.

Sync is off until the policy says `allow_sync: true`. `sync.hosts`, when it lists any, names the only servers that may be used, by host name (`github.com` for GitHub; a pattern such as `*.example.org` works). Both are checked in the app's own code at every use, not only on the page: with sync off, Settings › Git servers and a project's Sync section say so and offer nothing; connecting a host that is not listed is refused with a message naming the key; and a server connected before the policy changed stops syncing.

- **Settings › Git servers.** Connect GitHub, a GitHub Enterprise Server, a Gitea or a Forgejo with its address (https only) and a token, typed into a password field. A button opens the server's own page for making one: on GitHub a fine-grained token with Contents read and write (and Administration read and write, if Columbus should create repositories); on Gitea and Forgejo, Settings › Applications, with the scopes `read:user` and `write:repository`. Columbus asks the server whose token it is, and only then keeps it and shows the account. Connecting the same server again replaces its token (one account for each server). The token is kept only in the operating system's credential store (service `columbus-app`, account `git-server:<id>`), the way the app keeps its AI key: never in a file, a log, an error message or anything a page can read back. On Linux, where Columbus has no credential store it can use yet, no server can be connected. The servers themselves are listed in `git-servers.yaml` in the app's settings folder (F-18): `id`, `kind` (`github` or `gitea`), `url`, `user`. Where a server needs the organization's own certificate file, the file's path is kept with the app's data (`sync/server-certificates.json`), not in that list. **Remove** deletes the token too; projects linked to that server keep their files and their link.
- **Link.** On a project's page, **Link this project** takes one of the account's repositories, another one written as `owner/name`, or a new private one that Columbus creates, and a branch (the repository's own unless another is chosen). Linking sends none of the project's files. The link and the last synced state are kept in the app's data (`sync/<project>.json`), never in the files that sync, and hold no token. **Disconnect** forgets the link and leaves the files alone, here and on the server.
- **Check for changes** only reads. It compares the folder, the server and what was last synced, and lists what changed here, on the server and on both sides, and what is not syncing and why. It also runs once when the page opens. **What changed** shows a text file's two versions side by side.
- **Sync** gets the server's changes first, then sends the person's as one change, with their note ("What did you change?") as its message. It sends only what the last check listed: a file that changed after the person looked waits, and the page says so. A file a colleague deleted is moved to the computer's trash (the Recycle Bin on Windows), or to a folder in the app's data (`sync/<project>-removed/`) where the system has no trash for it; the page says which. It is never erased. **History** lists the branch's latest 30 changes: who, when, and their note.
- **A file changed on both sides is never merged or overwritten.** The server's version keeps the name, the person's is kept beside it as `name (my copy YYYY-MM-DD).ext`, and the file is listed under **Needs a look** with three choices: **Keep mine** (the copy takes the name back and goes with the next sync), **Keep theirs** (the copy goes to the trash) and **Keep both** (the copy stays, as a file of its own). A file deleted on one side and changed on the other needs a look too, and the changed version is the one kept. Until the person chooses, the copy does not sync. A difference in line endings alone is not a change (and line endings are never converted), and two sides that made the same change are not in conflict.
- **What never syncs.** Data, keys and outputs: `.env*`, `.pem`, `.key`, `.pfx`, `.p12`, `.sde`, `.ags`, `.gpkg`, the parts of a shapefile (`.shp`, `.shx`, `.dbf`, `.prj`, `.cpg`, `.sbn`, `.sbx`), `.tif`, `.tiff`, `.las`, `.laz`, `.zip`, the folders `outputs/`, `__pycache__/`, `.venv/` and `*.gdb/`, and the systems' own `.DS_Store`, `Thumbs.db` and `desktop.ini`. Files over 5 MB. Links (never followed, here or from the server), submodules and Git LFS pointers. Names that a Windows PC could not hold or that could do harm: `..`, `.git`, `.columbus`, Windows' reserved names and characters, a name ending in a dot or a space, invisible characters, two names that differ only by case, and paths longer than 200 characters. Each one is named under "Not syncing" with its reason, and none of them stops the rest. A folder may hold up to 20,000 files, and one sync sends up to 64 MB (what is left goes with the next).
- **Something that looks like a secret stops the sync.** Before anything is sent, outgoing text is searched for a private key (`-----BEGIN … PRIVATE KEY-----`), a GitHub token, a signed web token (JWT), 40 hex digits beside a word such as `token` or `secret` (Gitea's token shape), a quoted password or key assignment, an address with a password in it, and the server's own token. A hit stops the sync before anything is sent and names the file and the line, never the secret. There is no switch to send it anyway: take the secret out of the file, or move the file into `outputs/`.
- **The project's shared settings** (its name and its instructions for the assistant) travel as `columbus-project.yaml` at the top of the folder. Columbus writes the file when the person changes them. A changed one that arrives is never used by itself, because instructions steer the assistant: the page shows the old and the new name and instructions, and the project keeps its own until the person chooses **Use the new ones** (saved through the project's normal save, with its checks) or **Keep mine** (they are not offered again, and nothing is sent because of it).
- **Never forced (R-24).** What is sent says which state of the branch it was made from, and the server refuses it if the branch has moved since. Columbus then reads the server again and runs the whole sync again, up to five times, and after that stops and says so. It never overwrites what is on the server.
- **The network.** The server's certificate is always checked, against the system's trust store and, if one was given for that server, the organization's certificate file (`.pem`); there is no switch to skip the check. The token goes only to the server's own address: a redirect to another host is not followed, and the sync stops with a message. Requests have time limits, and refusals are said in plain words (a wrong or expired token, no permission, not found, rate limited, a server too old).
- **Servers.** GitHub and GitHub Enterprise Server through the REST API (`https://api.github.com`, `https://HOST/api/v3`). Gitea 1.20 or later, and Forgejo, through `/api/v1`; an older server is refused with a message naming its version. Repositories with SHA-256 object ids work. The first sync into an empty GitHub repository makes two entries in its history (GitHub takes a first file before it takes anything else); every other sync makes one.

**Honest limits.** This is not a Git clone: there is no history on the PC, no branches to switch between and no line-by-line merge; a project follows one branch of one repository; and sync is never automatic. GitHub's device sign-in is not offered (a token is). A file's "may run as a program" mark is sent from a Mac or Linux and left as the server has it from Windows. Sync was built and tested against stand-in servers written from GitHub's and Gitea's published API descriptions ([`crates/sync/tests/support`](../crates/sync/tests/support)), never against github.com, a GitHub Enterprise Server, a Gitea or a Forgejo itself. The app's pages for it are tested on Linux only (as all the app's pages are), with a stand-in holding the token; keeping it in Windows Credential Manager or the macOS Keychain goes through the same code as the app's AI key. Treat the first sync with a real server as the test it is: try it on a repository that does not matter yet.

## Build and run

Requires Rust (stable, 1.89+) and Python 3.12+. For the GIS tools, `pip install --require-hashes -r workers/python/requirements-gis.txt` (geopandas, pyogrio, shapely, pyproj, rasterio; the wheels include GDAL and PROJ); for project databases, also `pip install --require-hashes --no-deps --only-binary :all: -r workers/python/requirements-projectdb.txt` (DuckDB and its spatial extension; they then work offline). For PostGIS, Oracle and SQL Server, also `pip install --require-hashes -r workers/python/requirements-gis.txt -r workers/python/requirements-db.txt` (psycopg, oracledb, pyodbc; SQL Server also needs Microsoft ODBC Driver 18 for SQL Server).

**Pinned engine (REQ-21).** Every engine requirement file is generated from a `.in` source beside it (the ranges, and why each package is there) by `python packaging/engine/compile-requirements.py`: `uv pip compile --universal --python-version 3.12 --generate-hashes`, so each `.txt` pins every package, dependencies included, to one exact version with the SHA-256 of every file PyPI has for it, for every system at once; `requirements-db.txt` and `requirements-ci.txt` are resolved with the earlier files as constraints, so shared packages agree and they install side by side. After resolving, the script checks that each pinned version has a wheel for Windows x64, macOS arm64 (15 or later) and Linux x64 on CPython 3.12 and 3.13, and stops naming any package that doesn't. `--upgrade` moves every package to the newest version its range allows; DuckDB and its spatial extension are exact in their `.in` and move together by hand. The setup scripts, CI and the release's setup check install every file with `--require-hashes` (and `--no-deps --only-binary :all:` for `requirements-projectdb.txt` and `requirements-uv.txt`), so a file whose bytes differ from its pinned hash is refused. CI's test-only packages (playwright, selenium, pyyaml) come from `requirements-ci.txt`, pinned the same way; psycopg comes from `requirements-db.txt`. Updates: the weekly Engine requirements workflow (`.github/workflows/engine-requirements.yml`) runs the script with `--upgrade` and, when anything changed, pushes a `deps/engine-requirements-<date>` branch, starts CI on it and opens a pull request; `.github/dependabot.yml` updates crates, npm packages and GitHub Actions weekly (its pip entry opens no version updates, because GitHub doesn't document regenerating these files).

**Engine tests in CI (REQ-22).** Tests that need the GIS engine skip without it, except where `COLUMBUS_TEST_REQUIRE_ENGINE=1`, which every CI job that installs the engine sets: there they fail, naming the variable. The Rust tests find their Python through `crates/gateway/tests/support/mod.rs` (`COLUMBUS_PYTHON`, then `python3`, then `python`); a probe that imports the engine's modules and no database driver counts as an engine probe. The Python tests use `workers/python/tests/engine_required.py`. Skips for a database host that isn't set, a machine that can't confine, or no network are unaffected.

### Where it looks

| What | Windows default | Override |
| --- | --- | --- |
| Organization policy | `%ProgramData%\Columbus\policy.yaml` | `COLUMBUS_POLICY` |
| Connections (one YAML each) | `%APPDATA%\Columbus\connections\` | `COLUMBUS_CONNECTIONS` |
| Session workspaces | `%LOCALAPPDATA%\Columbus\workspaces\<session>` | `COLUMBUS_WORKSPACES` |
| The person's notes and own tools | `notes\` and `tools\` beside the workspaces | `COLUMBUS_NOTES`, `COLUMBUS_TOOLS` |
| Python environments | `environments\` beside the connections; created ones in `envs\` beside the workspaces | `COLUMBUS_ENVIRONMENTS`, `COLUMBUS_ENVS` |
| Audit log | `%ProgramData%\Columbus\audit\YYYY-MM.jsonl` | `COLUMBUS_AUDIT_DIR` |
| Engine worker | `workers\python\columbus_worker.py` beside the executable | `COLUMBUS_WORKER` |
| Python | `python.exe` on PATH | `COLUMBUS_PYTHON` |

On macOS the defaults are `/Library/Application Support/Columbus` (the organization's) and `~/Library/Application Support/Columbus` (yours); on Linux, `/etc/columbus` and the XDG folders. Without a policy file the server runs with safe defaults: local GeoPackage, SQLite, shapefile, file geodatabase and `files` (folders of CSV, Excel, GeoJSON, GeoParquet, KML and FlatGeobuf files) connections only (`file`, the old name of the last, is read as `files`), read-only, no scripts, no edits. See [`examples/`](../examples) for a policy and connections.

If the audit folder is not writable (a per-user install without the installer's permissions), the server falls back to a folder under the user's profile and says so in `whoami`. A call that cannot be audited does not run.

### Check the audit log

```powershell
columbus-mcp audit verify "%ProgramData%\Columbus\audit\2026-11.jsonl"
```

Each line records user, client, tool, connection, tables, row count, decision and a hash of the exact request; never row data. Editing, removing or reordering a line breaks the chain at that line.

## Not in this release

What Columbus 0.14.0 does not do, so nobody counts on it:

- Streamable HTTP transport (MCP over stdio only); confinement level C on Windows; Windows' own MCP containment.
- Reading enterprise geodatabases through ArcPy (`sde`), edits to Oracle, SQL Server or Esri geodatabases, and an ArcPy worker; arcpy runs only in a trusted environment (experimental), not in personal tools or workflows.
- A personal tool importing an environment's other packages beyond the tool rules' module list (CR-1, sent to Blueprint for a decision).
- Point clouds (`pointcloud_pipeline`, PDAL), mosaicking, STAC and EPT fetching, GeoParquet results and exports, a spatial index in streamed GeoPackages, export as a runnable script.
- Topology, tolerance and data-dictionary checks; domains enforced in verification.
- Web layers that need a user name and password, and web layers in `map_snapshot`.
- Deciding other AI apps' approvals inside the Columbus app; work-account AI providers (Copilot, Azure OpenAI, Vertex) for the app's chat; a code-signed app or `.mcpb`.
- The RustGIS native worker (its thousand tools come instead from the GeoLibre toolbox, [Toolboxes](#toolboxes)); QGIS as a toolbox kind; toolbox tools as workflow steps.
- In sync with GitHub and Gitea: GitHub's device sign-in, merging line by line, more than the one linked branch, and syncing by itself (D-20).
- A documentation website (CR-3, a later round).

Companion repository: [`geo-registry`](https://github.com/wiatrek-kevin-s/geo-registry) (open catalogue of GIS tools and data sources). The context pack format ([docs/context-pack.md](context-pack.md)) and the [skills library](../skills) live in this repository.

## Honest limits

The server's checks are a second line of defence. The guarantee nothing bypasses is the database's own users, roles and grants: give Columbus a read-only database login. Anyone with direct credentials and other tools can go around Columbus.

Performance: on a table with a row filter, the server keeps the database from merging the filtered table into the query, so that a caller's conditions never run on rows the filter excludes. On PostgreSQL that also stops the caller's own spatial conditions from using the spatial index: they are tested on every row the filter allows. On Oracle, the index operators (`SDO_RELATE`, `SDO_FILTER`, `SDO_WITHIN_DISTANCE`) need the indexed column itself and fail on a row-filtered table (`ORA-13226`); use `SDO_GEOM.RELATE` or `SDO_GEOM.SDO_DISTANCE` there, or `query_features` with a bbox. Tables without a row filter are not affected.

**Bbox pushdown (T-13, REQ-19).** A `query_features` bbox is not subject to the paragraph above: the gateway builds the bbox condition itself and puts it *inside* the filtered table, beside the row filter (and inside the barrier), where the source's spatial index applies: `geom && <schema>.st_makeenvelope(xmin, ymin, xmax, ymax, srid)` on PostGIS (the column's typed SRID; an untyped `geometry` column, SRID 0, is not pushed); `rowid IN (SELECT id FROM rtree_<table>_<geom> WHERE minx <= xmax AND maxx >= xmin AND miny <= ymax AND maxy >= ymin)` on GeoPackage when the table has its R-tree, one integer primary key and SQLite has the R-tree module; `MDSYS.SDO_FILTER(geom, MDSYS.SDO_GEOMETRY(2003, srid, NULL, MDSYS.SDO_ELEM_INFO_ARRAY(1, 1003, 3), MDSYS.SDO_ORDINATE_ARRAY(...))) = 'TRUE'` on Oracle when the listing finds a valid spatial index on the column (SDO_FILTER fails without one); `geom.Filter(geometry::STGeomFromText('POLYGON ((...))', srid)) = 1` on SQL Server `geometry` columns. A bbox in another CRS is first moved to the dataset's CRS by the engine (`bbox_to_dataset`, the same `transform_bounds` box `query_layer` uses), so both work on one box. On Oracle geodetic layers the box sent to the index is 0.001° larger on each side (Oracle treats a geodetic rectangle's edges as lines of latitude) and boxes wider than 119° of longitude are not pushed; boxes without area are not pushed on Oracle or SQL Server. The condition only narrows by envelope: the engine still keeps exactly the rows whose geometry meets the box, so the rows are the same as without it. Not pushed (every row the filters keep is read, then filtered by the engine, as before): SQL Server `geography`, sources with no usable index, shapefiles and file geodatabases (GDAL's SQLite dialect), and any query where the condition cannot be placed. Row filters and hidden fields apply unchanged. Each bbox result carries an info check `query.bbox_index` saying which way it went, and `executed_sql` shows the condition. A `files` connection's cache GeoPackage has an R-tree per geometry table (built with the table; cache build 4, so older caches rebuild once), registered as `gpkg_rtree_index` without triggers, since only the cache builder writes it. The PostGIS fixture has a GiST index and the SQL Server fixture a spatial index for these tests; Oracle's `ROUTES` stays unindexed as the no-index case.

Trusted environments (experimental) are outside Columbus's control by design: Columbus labels and checks what comes back through it, never what the script does directly. On Unix a process a trusted script starts in a new session or process group of its own escapes its process group and is not ended with it. On Windows a trusted run, an environment probe and environment creation run in a job object of their own, so everything they start ends with them; if the job object cannot be made (a very old Windows), the run goes ahead and is ended with `taskkill /T` instead, which reaches only processes still linked to it.

Database settings outside the server's reach:
- Leave PostGIS raster out-of-database bands (`postgis.enable_outdb_rasters`) and `postgis.gdal_enabled_drivers` at their defaults (off); with them on, raster functions can read files on the database server.
- Allowing a parent table allows its rows in every child table and partition; deny or filter at the parent.
- Functions and types in the database are trusted only when PostgreSQL's built-ins or the PostGIS extension provide them. The engine always searches `pg_catalog` first, and PostGIS functions are called by the extension's own schema.
